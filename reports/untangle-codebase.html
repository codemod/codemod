How to read this

The skill asks one question of the codebase: should these pieces change together? Problems fall into three wrong answers plus special cases.

  • Hidden link — pieces that must change together, but the code does not show it.
  • Needless link — pieces tied together that change for different reasons.
  • Surplus — pieces with no reason of their own to change (wrappers, dead, speculative).
  • Special case — code for one situation instead of a design that accounts for it.

Safety is risk of applying the proposed fix (behavior, schema, cancellation, CI/JSONL). Impact is how much the fix would help agents (read less, break less silently, debug faster). Prioritize high-impact / low-or-medium-safety first; schedule high-safety work with a plan and tests.

F1 · Make terminal ownership a single typed mode

Rank 1 CLI / Core / Runners Impact high Safety medium

Introduce one RunPresentationMode { Text | Quiet | Tui | Jsonl } applied once when constructing the engine/runner. Non-CLI crates return structured lines/events; CLI alone renders. Delete quiet dual-writes and scattered println! policy.

Why this is the top pick: the repo already documents this rule, but call sites still hand-apply quiet flags. Fixing it removes a whole class of TUI/JSONL silent breaks agents keep reintroducing. Git shows run.rs / workflow/run.rs / jssg/run.rs as high-churn (54 / 34 / 46 commits since Aug 2025).

Safety notes: user-visible output and CI JSONL change shape. Mitigate with golden CLI tests for text/quiet/jsonl and a TUI smoke path. Do not change workflow semantics.
