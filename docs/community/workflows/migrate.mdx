Codemods written as `workflow.yaml` keep working: the CLI translates them into the equivalent [`workflow.ts`](/community/workflows/reference) when they run. You don't need to change anything to keep using or publishing them.

Convert a codemod to `workflow.ts` when you want what TypeScript workflows add: inline `forEachFile` callbacks, ordinary control flow instead of `depends_on` and `if:`, step results you can use in later steps, and [tests that run the whole workflow](/community/workflows/testing).

## Convert a codemod

In the package directory, preview the result, then convert:

```bash
npx codemod workflow upgrade --dry-run
npx codemod workflow upgrade
```

You can also pass a single workflow file, for example `npx codemod workflow upgrade workflows/main.yaml`. If the package manifest points to that file, upgrade updates the entry to the new TypeScript file.

`upgrade` writes `workflow.ts` next to `workflow.yaml`, points `codemod.yaml` at it, and removes the YAML file. Keep the YAML file with `--keep-yaml`. In a repository with many packages, run it once at the root to convert them all.

For example, this `workflow.yaml`:

```yaml workflow.yaml
version: "1"
nodes:
  - id: apply-transforms
    name: Apply AST Transformations
    type: automatic
    steps:
      - name: Replace deprecated header fields
        js-ast-grep:
          js_file: scripts/codemod.ts
          language: typescript
          include: ["**/*.ts", "**/*.js"]
          exclude: ["**/node_modules/**"]
```

becomes:

```ts workflow.ts
// Generated from workflow.yaml by `codemod workflow upgrade`.
import { parse } from "codemod/ast-grep";
import { forEachFile, step } from "codemod/workflow";
import transform from "./scripts/codemod.ts";

export default async function main() {
  // Apply AST Transformations
  await step(
    "Replace deprecated header fields",
    forEachFile(
      {
        include: ["**/*.ts", "**/*.js"],
        exclude: ["**/node_modules/**"],
        language: "typescript",
      },
      (file) => {
        const out = transform(parse(file));
        if (typeof out === "string") file.write(out);
      },
    ),
  );
}
```

Your transform files don't change. The workflow imports each one and calls it from a `forEachFile` callback, as the YAML step did: `parse(file)` gives the root, with the step's semantic analysis, and the text it returns is written with `file.write`. When the transform reads its options, it gets them (`params`, `language`, `targetDir`, and `matrixValues` in a matrix); with a `getSelector`, files without a match are skipped and the matches are `options.matches`; and when it returns `{ edit, data }`, the callback writes `edit` and returns `data`, which the step collects into its `outputs`. A selector several steps share becomes one `const`.

Two things a plain callback cannot do: `root.rename()` (in a callback, that is `file.rename()`) and `jssgTransform` on other files. A transform that uses either (or a file of the package it imports does) runs through `jssgFile` from `codemod-internal:jssg-compat`, a compatibility adapter that runs it as workflow.yaml's `js-ast-grep` step did; `upgrade` says which transform and why. The `codemod` package ships its types.

Your fixture tests keep working when you do. Make the transform file's default export a callback, and add `--callback` to its test command; the fixture folders stay as they are:

```ts scripts/codemod.ts
import { parse } from "codemod/ast-grep";
import type { FileCallback } from "codemod/workflow";

// Before: export default function transform(root) { ...; return text; }
const migrate: FileCallback = (file) => {
  const root = parse(file);
  // ... the transform's body, unchanged ...
  if (text) file.write(text);
};
export default migrate;
```

```diff package.json
- "test": "npx codemod jssg test -l typescript ./scripts/codemod.ts"
+ "test": "npx codemod jssg test --callback -l typescript ./scripts/codemod.ts"
```

The workflow then imports it (`import migrate from "./scripts/codemod.ts"`) and gives it to `forEachFile`. A transform that read `options.params` reads them in the workflow instead; see [Test a forEachFile callback](/community/jssg/testing#test-a-foreachfile-callback).

If `upgrade` suggests it, add the `codemod` package as a dev dependency, so your editor type-checks `workflow.ts`:

```bash
npm install --save-dev codemod
```

## How YAML maps to TypeScript

| `workflow.yaml` | `workflow.ts` |
| --- | --- |
| A node | An `async` function. A workflow with one plain node runs its steps in `main` |
| `depends_on` | Functions called in order; independent nodes run at the same time |
| A step | `await step("<step name>", <task>)` |
| `js-ast-grep` | `import transform from "./<js_file>"` and `forEachFile({ include, exclude, language, semanticAnalysis, capabilities }, (file) => { const out = transform(parse(file)); ... })`. A transform that calls `root.rename()` or `jssgTransform` runs through the compatibility adapter, `jssgFile` |
| `ast-grep` | `import rules from "./<config_file>"` and `forEachFile({ include, exclude }, astGrep(rules))`. A `base_path` is joined to the globs (`base_path: app` with `include: ["src/**"]` gives `include: ["app/src/**"]`); `max_threads` is dropped |
| `run` | `shell(command, { env })` |
| `codemod` | `codemod(source, { params })` |
| `ai` | `agent(prompt, { ... })` |
| `install-skill` | `installSkill({ ... })` |
| `matrix` (`values` or `from_state`) | One call per value, run at the same time; one at a time when the node uses git (`branch_name`, `pull_request`, step `commit`) |
| `shard` | `shard({ method, target, files, filter, previous })`, its result passed to the steps that use it. A shard `function` is imported; the shard's `js-ast-grep` transform becomes a `filter` that keeps the files it would change |
| `if:` | An `if` statement whose condition runs through `__evaluate(...)`, the YAML engine's own evaluator, so it means exactly what it did |
| `${{ params.name }}` | `params.name`. In a list field, such as `include` or a commit's `add`, a value that is an array expands into one entry per item, as before. Inside any other text it becomes `asText(params.name, "params.name")`, which prints arrays and objects as JSON and null as nothing, and fails if the value is not set, as workflow.yaml did. Strings are printed as written (workflow.yaml printed `"007"` as `7`), and an object's integer-like keys such as `"10"` come first, in numeric order, as in JavaScript |
| `${{ state.name }}` | `state.name`, a local object. Shell steps get it as `CODEMOD_STATE_<KEY>` variables, and the lines they write to `$STATE_OUTPUTS` are printed at the end of their stdout and copied into it by `applyStateOutputs`. JSSG transforms that call `getState` or `setState` cannot be translated; `upgrade` flags them |
| `trigger: manual` | `await step(approval("<node name>"))` |
| `branch_name`, `pull_request`, step `commit` | `branch`, `pullRequest` and `commit` steps, imported from `codemod/git` |
| `templates` and `use:` | Functions |

Fields that never had an effect, such as `codemod.args` or template `outputs`, are left out. `upgrade` and `codemod workflow validate` list them, and `upgrade` leaves a `// codemod upgrade:` comment where each one was.

## Check the converted codemod

Run your fixtures through the whole workflow from a test file, `tests/workflow.test.ts`:

```ts tests/workflow.test.ts
import { describe, test } from "node:test";
import { assertTree, fixtures, runWorkflow } from "codemod/testing";

const workflow = new URL("../workflow.ts", import.meta.url);

describe("my-codemod", () => {
  for (const fixture of fixtures(new URL("./fixtures", import.meta.url))) {
    test(fixture.name, async () => {
      const run = await runWorkflow(workflow, { target: fixture.input, params: fixture.params });
      assertTree(run, fixture.expected);
    });
  }
});
```

```bash
node --test "tests/**/*.test.ts"
```

`fixtures` reads the same layouts as `codemod jssg test`; point it at the directory that holds your fixtures. See [Testing workflows](/community/workflows/testing).

## What behaves differently

Most codemods run exactly as before. These are the differences, for both `workflow.yaml` and `workflow.ts`:

- **Modules are imported as `codemod/workflow`, `codemod/ast-grep`, and so on.** `upgrade` writes the new spelling. Imports of the older `codemod:workflow` spelling, in workflows and in transforms, keep working and name the same modules.
- **Semantic analysis is on by default for `jssg` steps.** Transforms get file-scope semantic analysis, as they do with `codemod jssg run` and `codemod jssg test`, so `definition()` and `references()` work in workflows too. Before, they returned nothing in workflows. Turn it off with `semantic_analysis: none` (YAML) or `semanticAnalysis: "none"` (TypeScript).
- **A step `if:` that fails to evaluate is reported.** The step is still skipped, as before, and the run's log says why.
- **`runtime: docker` and `runtime: podman` are not supported yet.** `workflow run` and `workflow upgrade` refuse a workflow that uses them, before anything runs. Keep running it with `npx codemod@1`.
- **Shell state output requires a POSIX shell.** On Windows, a translated workflow that needs `$STATE_OUTPUTS` fails before any step runs. Run it on a POSIX system, or port the workflow so steps pass results directly.
- **Transforms are pure.** A `jssg` transform that calls `fetch`, `child_process` or writes files with `fs` fails on each file, even with `capabilities` in `codemod.yaml` or `--allow-*` flags, which are now ignored for workflows. Reading the target with `fs` still works. Move network requests to an `http()` step and commands to a `shell` step before the transform runs, and give the transform what they returned. See [Callbacks are pure](/community/workflows/reference#callbacks-are-pure).
- **`state.schema` is accepted but not checked.**
- **Runs are resumed by id:** `codemod workflow resume --id <run-id>`. A manual node waits as an approval step; resume it with `--approve`. Runs started with an earlier CLI version can't be resumed.
- **`codemod workflow tui` was removed.** Runs show their progress in the terminal.

## Publishing workflow.ts codemods

Older CLI versions run `workflow.yaml` only. People who run a `workflow.ts` codemod need a CLI version that runs TypeScript workflows, which `npx codemod` always fetches.

Publishing includes every callback and shard function the workflow imports, and every YAML rule file it imports. That is why file paths are build errors: a path, especially one computed at run time, could be missing from the published package.

## Breaking changes in this alpha

A `workflow.ts` written for an earlier preview may need these changes. Each fails to build with a message that says what to write instead. `workflow.yaml` files need none: the translation does it for them.

- **`jssg(...)` was removed: per-file logic is a `forEachFile` callback.** Write it inline, or keep it in a file as that file's default export and import it:

  ```ts
  // Before
  await step(forEachFile({ language: "tsx" }, jssg("./scripts/codemod.ts", { params: { strict: true } })));

  // After
  import migrate from "./scripts/migrate.ts"; // export default (file) => { ... }
  await step(forEachFile({ language: "tsx" }, migrate));
  ```

  In the callback, `parse(file)` (from `codemod/ast-grep`) gives the root a transform got, `file.write(text)` replaces returning the text, `file.rename(path)` replaces `root.rename()`, and the value it returns is collected into `outputs` (where a transform returned `{ edit, data }`). Values a transform read from `options.params` become variables the callback captures. `semanticAnalysis` and `capabilities` are now selector options of `forEachFile`. `jssg(path, { reduce, initial })` becomes `forEachFile(selector, callback, reduce, initial)`: the reducer now gets `(result, output, path)` where it got `(result, { file, data })`, and the step's result has the folded value as `reduced` (see [Reducing outputs](/community/workflows/reference#reducing-outputs)). It folds outputs in path order as files finish, so the outputs of a large target are never all held in memory. `codemod jssg run` and `codemod jssg test` still run jssg transform files on their own, and `codemod jssg test --callback` runs a callback file on the same fixtures.
- **File paths were removed.** `forEachFile`, `shard` and `astGrep` take functions and rules, not paths:
  - `astGrep("./rules/config.yml")` → `import rules from "./rules/config.yml"` and `astGrep(rules)`, or rules written as objects: `astGrep({ id: "no-var", language: "javascript", rule: { pattern: "var $A = $B" }, fix: "let $A = $B;" })`;
  - `shard({ method: { function: "./scripts/shard.ts" } })` → an imported (or inline) shard function, `method: { function: shardFiles }`;
  - `shard({ jssg: { path, ... } })` → `filter: (file) => ...`, a callback that keeps the files it returns `true` for; `filePattern` → `files`.

- **`astGrep(rules)` runs only inside `forEachFile`.** It is no longer a step on its own, and its only option is `repeat`; the selector says which files:

  ```ts
  // Before
  await step(astGrep(rules, { include: ["src/**"], basePath: "app", threads: 4 }));

  // After
  await step(forEachFile({ include: ["app/src/**"] }, astGrep(rules)));
  ```

If your editor flags `.ts` in an import, add `"allowImportingTsExtensions": true` to `tsconfig.json`, as packages from `codemod init` have.
