Codemods written as `workflow.yaml` keep working: the CLI translates them into the equivalent [`workflow.ts`](/community/workflows/reference) when they run. You don't need to change anything to keep using or publishing them.

Convert a codemod to `workflow.ts` when you want what TypeScript workflows add: inline `forEachFile` callbacks, ordinary control flow instead of `depends_on` and `if:`, step results you can use in later steps, and [tests that run the whole workflow](/community/workflows/testing).

## Convert a codemod

In the package directory, preview the result, then convert:

```bash
npx codemod workflow upgrade --dry-run
npx codemod workflow upgrade
```

`upgrade` writes `workflow.ts` next to `workflow.yaml`, points `codemod.yaml` at it, and removes the YAML file. Keep the YAML file with `--keep-yaml`. In a repository with many packages, run it once at the root to convert them all.

For example, this `workflow.yaml`:

```yaml workflow.yaml
version: "1"
nodes:
  - id: apply-transforms
    name: Apply AST Transformations
    type: automatic
    steps:
      - name: Replace deprecated header fields
        js-ast-grep:
          js_file: scripts/codemod.ts
          language: typescript
          include: ["**/*.ts", "**/*.js"]
          exclude: ["**/node_modules/**"]
```

becomes:

```ts workflow.ts
import { jssg, step } from "codemod/workflow";

export default async function main() {
  // Apply AST Transformations
  await step(
    "Replace deprecated header fields",
    jssg("scripts/codemod.ts", {
      include: ["**/*.ts", "**/*.js"],
      exclude: ["**/node_modules/**"],
      language: "typescript",
    }),
  );
}
```

Your transform files don't change.

If `upgrade` suggests it, add the `codemod` package as a dev dependency, so your editor type-checks `workflow.ts`:

```bash
npm install --save-dev codemod
```

## How YAML maps to TypeScript

| `workflow.yaml` | `workflow.ts` |
| --- | --- |
| A node | An `async` function. A workflow with one plain node runs its steps in `main` |
| `depends_on` | Functions called in order; independent nodes run at the same time |
| A step | `await step("<step name>", <task>)` |
| `js-ast-grep` | `jssg(path, { include, exclude, language, ... })` |
| `ast-grep` | `astGrep(configFile, { ... })` |
| `run` | `shell(command, { env })` |
| `codemod` | `codemod(source, { params })` |
| `ai` | `agent(prompt, { ... })` |
| `install-skill` | `installSkill({ ... })` |
| `matrix` (`values` or `from_state`) | One call per value, run at the same time |
| `shard` | `shard({ ... })`, its result passed to the steps that use it |
| `if:` | An `if` statement whose condition runs through `__evaluate(...)`, the YAML engine's own evaluator, so it means exactly what it did |
| `${{ params.name }}` | `params.name` |
| `${{ state.name }}` | `getState("name")` |
| `trigger: manual` | `await step(approval("<node name>"))` |
| `branch_name`, `pull_request`, step `commit` | `branch`, `pullRequest` and `commit` steps |
| `templates` and `use:` | Functions |

Fields that never had an effect, such as `codemod.args` or template `outputs`, are left out. `upgrade` and `codemod workflow validate` list them, and `upgrade` leaves a `// codemod upgrade:` comment where each one was.

## Check the converted codemod

Run your fixtures through the whole workflow:

```bash
npx codemod workflow test
```

It reads the same `tests/` fixtures as `codemod jssg test`. See [Testing workflows](/community/workflows/testing).

## What behaves differently

Most codemods run exactly as before. These are the differences, for both `workflow.yaml` and `workflow.ts`:

- **Modules are imported as `codemod/workflow`, `codemod/ast-grep`, and so on.** `upgrade` writes the new spelling. Imports of the older `codemod:workflow` spelling, in workflows and in transforms, keep working and name the same modules.
- **Semantic analysis is on by default for `jssg` steps.** Transforms get file-scope semantic analysis, as they do with `codemod jssg run` and `codemod jssg test`, so `definition()` and `references()` work in workflows too. Before, they returned nothing in workflows. Turn it off with `semantic_analysis: none` (YAML) or `semanticAnalysis: "none"` (TypeScript).
- **A step `if:` that fails to evaluate is reported.** The step is still skipped, as before, and the run's log says why.
- **`runtime: docker` and `runtime: podman` are not supported.** Their steps run directly on the machine.
- **`state.schema` is accepted but not checked.**
- **Runs are resumed by id:** `codemod workflow resume --id <run-id>`. A manual node waits as an approval step; resume it with `--approve`. Runs started with an earlier CLI version can't be resumed.
- **`codemod workflow tui` was removed.** Runs show their progress in the terminal.

## Publishing workflow.ts codemods

Older CLI versions run `workflow.yaml` only. People who run a `workflow.ts` codemod need a CLI version that runs TypeScript workflows, which `npx codemod` always fetches.
