A workflow is a TypeScript file, `workflow.ts`, whose default export runs **steps**. This page documents everything you can import from `codemod/workflow`, and what else a workflow can import.

## Complete example

```ts workflow.ts
import { step, forEachFile, jssg, shell, approval } from "codemod/workflow";
import { parse } from "codemod/ast-grep";

const LEGACY = "moment";

export default async function main({ params }: { params: { replacement: string } }) {
  // Find the files that import the legacy library.
  const usages = await step("Find moment imports",
    forEachFile({ language: "typescript", containing: LEGACY }, (file) => {
      const root = parse(file);
      const found = root.root().findAll({ rule: { pattern: `import $X from "${LEGACY}"` } });
      return found.length ? file.path : undefined;
    }),
  );

  // Rewrite only those files.
  await step("Rewrite imports", forEachFile({ language: "typescript" }, (file) => {
    if (!usages.outputs.includes(file.path)) return;
    file.write(file.text.replaceAll(`from "${LEGACY}"`, `from "${params.replacement}"`));
  }));

  // Run an existing JSSG transform, then the formatter.
  await step("Apply transform", jssg("./scripts/codemod.ts", { include: "src/**/*.ts" }));
  await step(approval("Run the formatter?"));
  await step("Format", shell("npx prettier --write src"));
}
```

Run it with:

```bash
npx codemod workflow run -w . --param replacement=dayjs
```

## How a workflow runs

A workflow file contains three kinds of code, each with its own rules:

| Where | When it runs | Rule |
|---|---|---|
| Workflow body, outside any step | On every run and every resume | Deterministic; see [The workflow body](#the-workflow-body) |
| Inside a function step, `step(() => ...)` | Once, in its own isolate; its result is recorded | Outside variables arrive as frozen copies; the result must be JSON |
| Inside a `forEachFile` callback | Once per file, in parallel, in isolates | Outside variables arrive as frozen copies; changes go through the file object |

- **Steps are durable.** Each step's result is saved as soon as the step finishes. If a run fails or is canceled, `codemod workflow resume` replays the finished steps from their saved results and continues from the step that failed.
- **A step starts when you call `step()`.** `await` waits for it. `Promise.all([step(a), step(b)])` runs two steps at the same time.
- **Each step is identified by its order and content.** If you change a step that already finished and then resume, the run stops with a `NondeterminismError`, because the recorded result no longer matches. Changing the step that failed is fine; that is how you fix a run.

## `step(label?, task)`

Runs a task as a durable step and returns a promise for its result.

```ts
const result = await step("Rename files", forEachFile("src/**/*.less", (file) => {
  file.rename(file.path.replace(/\.less$/, ".css"));
}));
```

- **`label`** (optional): shown in progress output, `codemod workflow status` and errors. Defaults to a description of the task.
- **`task`**: `forEachFile(...)`, one of the [tasks](#tasks), or a function whose result should be computed once and recorded.
- **Result:** deeply frozen and read-only. Copy it before changing it.

### Function steps

A function step runs once, in its own isolate, and records what it returns. It may be async.

```ts
import { readFile } from "fs/promises";

const plan = await step("Plan batches", () =>
  usages.outputs.reduce((batches, path, index) => {
    (batches[index % 4] ??= []).push(path);
    return batches;
  }, [] as string[][]),
);
const config = await step("Read config", async () => JSON.parse(await readFile("codemod.config.json", "utf8")));
```

- Write the function inline, so the build can extract it. Outside variables arrive as frozen copies, with the same rules as [forEachFile callbacks](#using-outside-variables).
- Inside, `Date`, `Math.random`, `fetch`, `fs` and `child_process` are real, as far as the run allows (`--allow-fs`, `--allow-fetch`, `--allow-child-process`).
- The result must be JSON. On resume, a finished function step is replayed from its record; if you changed it, the run stops with a `NondeterminismError`.

## `forEachFile(selector?, callback)`

Runs `callback` once per selected file and returns a task for `step()`. Without a selector, it visits the files of the package's `targets.languages` in `codemod.yaml`.

### Selector

| Form | Example |
|---|---|
| A glob | `"src/**/*.less"` |
| A list of globs | `["**/*.ts", "**/*.tsx"]` |
| An object | `{ language: "tsx", exclude: "**/*.test.tsx", containing: "moment" }` |

Object fields:

| Field | Meaning |
|---|---|
| `include` | Glob or globs to select |
| `exclude` | Glob or globs to skip |
| `language` | Selects the language's file extensions when `include` is not set, and is the default language for `parse(file)` and `parse(text)` |
| `containing` | Only files whose text contains this string |
| `concurrency` | Files each worker keeps in flight (default `1`). Raise it for async callbacks that wait on the network or `codemod/llm` |

Files are selected as `jssg` and `astGrep` select theirs: `.gitignore` is respected, hidden files and directories (`.github/`) are included, and a `language` means the same extensions for all three (`"typescript"` also takes `.js` files, which that parser reads). A selector is plain data, so you can reuse and refine it: `{ ...sources, containing: "moment" }`.

### The file object

| Member | Meaning |
|---|---|
| `file.path` | Path relative to the target |
| `file.text` | Contents when the step started |
| `file.language` | The selector's `language`, if it has one |
| `file.write(text)` | Replace the contents |
| `file.rename(path)` | Move the file |
| `file.delete()` | Remove the file |

Changes are recorded, not written immediately. When every file is done, the step checks for conflicts and applies all changes together. Nothing is written when two files are renamed to the same path, when a file changed on disk since the step read it (another step or command edited it meanwhile), or when the run was canceled. If writing fails part-way, what was written is put back.

### The callback

- The callback may be async: `async (file) => { ... }`.
- Return a value to collect it; returned values become `result.outputs`, in path order. Return nothing to collect nothing.
- A callback that throws fails only that file; the error appears in `result.failures`.
- Metrics recorded with [`codemod/metrics`](/community/jssg/metrics) appear in `result.metrics` and in the run's report. Declare the metric at module level and record it in the callback.

```ts
import { useMetricAtom } from "codemod/metrics";

const rewrites = useMetricAtom("rewrites");

export default async function main() {
  const result = await step(forEachFile({ language: "tsx", concurrency: 4 }, async (file) => {
    const root = parse(file);
    const edits = root.root().findAll({ rule: { pattern: "moment($A)" } }).map((node) => node.replace("dayjs()"));
    rewrites.increment({ file: file.path }, edits.length);
    if (edits.length) file.write(root.root().commitEdits(edits));
  }));
  result.metrics.rewrites; // [{ cardinality: { file: "src/a.tsx" }, count: 2 }, ...]
}
```

### Result

```ts
{
  outputs: unknown[];
  changes: { written: string[]; renamed: { from: string; to: string }[]; deleted: string[] };
  failures: { path: string; error: string }[];
  metrics: Record<string, { cardinality: Record<string, string>; count: number }[]>;
}
```

### Using outside variables

A callback (or function step) runs in its own isolate, so the build copies in what it needs:

- **Module-level constants, functions and classes** it uses are copied in.
- **Local variables of the surrounding function** are passed in as frozen copies when the step starts. They must be JSON values.
- **Imports** it uses are available: `codemod/ast-grep`, `codemod/metrics`, `codemod/runtime`, Node-style modules (`path`, `fs` with `--allow-fs`, ...), npm packages and files next to the workflow (`import { rule } from "./lib/rules.ts"`).
- **State:** `getState`, `setState`, `unsetState` and `acquireLock` from `codemod/workflow` work as in [JSSG transforms](/community/jssg/advanced/workflow). Prefer returning values: outputs are ordered and need no locks.

These are build errors, reported with the file, line and column:

- assigning to a variable declared outside the callback (return a value instead);
- using a local variable that is reassigned after it is declared;
- using a function or class declared inside the surrounding function (move it to module level);
- calling `step()`, `forEachFile` or another task inside the callback;
- passing a callback by name instead of writing it inline;
- calling `forEachFile`, or `step` with a function, in a file the workflow imports: callbacks are only extracted from the workflow file itself;
- importing `codemod/workflow` as a namespace (`import * as`): import `step`, `forEachFile` and the rest by name.

A local that is not JSON (a `Set`, a `Map`, a class instance) fails when the step starts, naming the variable.

## Parsing with `codemod/ast-grep`

```ts
import { parse } from "codemod/ast-grep";

parse(file);                        // a forEachFile file; root.filename() is its path
parse(file, { language: "tsx" });
parse(text);                        // in a forEachFile callback whose selector names a language
parse(text, { language: "tsx" });
parse("tsx", text);                 // the original JSSG form
```

`parse` returns the [ast-grep](/community/jssg) root. The language comes from the options, then the file, then the step's selector, then the file extension. Files you only rename are never parsed.

## The workflow body

The body is the code outside steps and callbacks. It runs again on every resume and must issue the same steps each time, so:

- **Pure modules are available:** `path`, `url`, `util`, `buffer`, `string_decoder`, `assert`, `events`, `zlib`, `codemod/ast-grep`, and npm packages or local files whose imports only reach these.
- **Modules that touch the outside world are build errors in the body:** `fs`, `child_process`, `os`, `process`, `crypto`, timers, `codemod/llm`, and packages that import any of them. The error names the import chain, for example `file-reader/index.js → file-reader/read.js → node:fs`. Use them inside a step or callback instead.
- **`Date`, `Math.random`, `crypto.randomUUID` and `performance.now` are replay-safe.** Random numbers come from a generator seeded by the run, and the clock starts at the run's start time and moves only when a step finishes, to the time recorded for it.
- **Metrics** can be declared in the body (`useMetricAtom`) but only recorded inside steps and callbacks.
- **`console.log`** goes to the run's output.

## Tasks

| Task | What it does |
|---|---|
| `jssg(path, options)` | Run a [JSSG](/community/jssg) transform file. Options: `include`, `exclude`, `basePath`, `files`, `language` (default `typescript`), `params`, `matrix`, `capabilities`, `semanticAnalysis` (`"file"` by default, as in `jssg run`; also `"workspace"` or `"none"`), `threads`, `dryRun`. Result: `{ changes, unmodified, failures }`. |
| `astGrep(path, options)` | Apply an ast-grep YAML rule file. Options: `include`, `exclude`, `basePath`, `threads`. |
| `shell(command, { env, cwd })` | Run a shell command. Result: `{ output }`. |
| `shard(options)` | Split files into groups. See [Sharding](/community/workflows/sharding). |
| `codemod(source, { params })` | Run another codemod package (registry name or local path) as part of this step. |
| `agent(prompt, options)` | Hand a prompt to a coding agent. See [Coding agents](#coding-agents). |
| `installSkill({ package, path, harness, scope, force })` | Install a package's agent skill. |
| `approval(message)` | Wait for a person to approve. See [Approvals](#approvals). |
| `branch(name)`, `commit(message, { add, allowEmpty })`, `pullRequest({ title, body, draft, base })` | Git automation. These only touch git when the run uses `--managed-git`; otherwise they are recorded as skipped. |

Paths given to `jssg`, `astGrep` and shard functions are relative to the workflow file.

### Shell commands

`shell` commands get these environment variables:

| Variable | Value |
|---|---|
| `CODEMOD_PATH` | The workflow's directory |
| `CODEMOD_STATE` | A file containing the workflow state as JSON |
| `CODEMOD_STATE_<KEY>` | Each state value, JSON-encoded |
| `STATE_OUTPUTS` | A file the command can write `key=value` (set) or `key@=value` (append) lines to; they become workflow state |

Shell commands, agents and skill installs are skipped in a dry run, and function steps and `forEachFile` callbacks run without `fs` and `child_process`, whatever capabilities the run has: a dry run changes nothing.

### Coding agents

`agent(prompt, options)` runs a coding agent installed on the machine, without asking it questions, in the run's target directory:

```ts
const review = await step(
  "Fix the remaining call sites",
  agent("Replace the remaining moment() calls in src/ with dayjs().", {
    agent: "claude-code",
    model: "sonnet",
    timeoutSeconds: 600,
  }),
);
console.log(review.result);
```

Its result holds the agent's final answer (`result`), its `sessionId`, `model` and `usage` (tokens and cost, as far as the agent reports them). What the agent does, such as its messages, tool calls and commands, shows in the run's output as it happens.

| Option | |
| --- | --- |
| `agent` | Which agent to run. It must be installed |
| `systemPrompt` | Extra instructions. Agents with an option for them get them there; the others get them in front of the prompt |
| `model` | A model name the agent understands |
| `autonomy` | `"full"` (default): the agent edits files and runs commands without asking. `"read-only"`: the agent reads and answers only. The step fails before it starts when the agent cannot be kept read-only; see the table below |
| `timeoutSeconds` | Stop the agent after this long |

When the agent fails, is stopped or runs out of time, the step fails; the step's output then says which session the agent had started and what it had used, when the agent reported them.

Supported agents, by the id `agent` takes:

| Agent | Id | Read-only | Notes |
| --- | --- | --- | --- |
| Claude Code | `claude-code` (or `claude`) | Yes: plan mode | |
| Codex | `codex` | Yes: read-only sandbox | Runs outside git repositories too |
| Cursor Agent | `cursor` | Yes: ask mode | |
| Gemini CLI | `gemini` | Its defaults | Older versions give text only |
| Antigravity CLI | `antigravity` (or `agy`) | Its defaults | |
| OpenCode | `opencode` | Yes: plan agent | `model` is `provider/model` |
| GitHub Copilot CLI | `copilot` | Its defaults | |
| Amp | `amp` | No | Picks models by mode, so `model` is ignored |
| Qwen Code | `qwen-code` (or `qwen`) | Yes: plan mode | |
| Goose | `goose` | Yes: chat mode | |
| Factory Droid | `droid` | Its defaults | |
| Kimi Code | `kimi` | No | Always runs in Kimi's auto mode |
| Crush | `crush` | No | Text output only; approves every action itself |
| OpenClaw | `openclaw` | No | Reports once, at the end |
| Aider | `aider` | Yes: ask mode | Text output only; never runs the shell commands it suggests |
| Kiro CLI | `kiro` | Its defaults | Text output only |
| Auggie | `auggie` | No | Text output only; tool permissions come from its settings |
| Cline | `cline` | Yes: no auto-approval | Text output only |

The **Read-only** column says what `autonomy: "read-only"` does for each agent:

- **Yes**: the agent runs in its own read-only mode.
- **Its defaults**: the agent runs without the option that lets it act freely. Left to its defaults it asks before it writes a file or runs a command, and with nobody to answer, it does neither. If your own configuration of the agent approves actions in advance, they still run.
- **No**: the agent cannot be kept from writing. A read-only step that names it fails before the agent starts, and the agent is not offered when you pick one for a read-only step.

Some agents take the prompt on their command line and not on their input: Cursor Agent, Gemini CLI, Antigravity CLI, GitHub Copilot CLI, Qwen Code, Kimi Code, Crush, Aider, Kiro CLI, Auggie and Cline. For these, a prompt (with `systemPrompt`, for those that take it in front of the prompt) larger than 100 KiB fails the step before the agent starts.

Without `agent`, the step uses:

1. the run's agent: `codemod workflow run --agent codex`, or the `LLM_AGENT` environment variable;
2. the coding agent the workflow itself runs inside, for example when Claude Code runs `codemod run`. The prompt goes back to it in the step's output, and the step succeeds with `handedOff: true`;
3. an agent you pick from the installed ones, when the run is interactive;
4. the built-in agent, when `LLM_API_KEY` is set (with `LLM_PROVIDER`, `LLM_MODEL` and `LLM_BASE_URL`).

Otherwise the prompt is printed as instructions and nothing runs.

## State

Workflow state is a set of named JSON values shared by the workflow and the steps it runs.

```ts
import { step, shell, getState, setState } from "codemod/workflow";

setState("target", "react-19");
await step(shell('echo "version=19" >> "$STATE_OUTPUTS"'));
getState("version"); // 19
getState();          // { target: "react-19", version: 19 }
```

- **In the workflow:** `getState(key)` reads a value; `getState()` returns all of them. `setState(key, value)` sets one.
- **In JSSG transforms:** `setState`, `getState`, `unsetState` and `acquireLock` from `codemod/workflow`. See [Workflow context](/community/jssg/advanced/workflow).
- **In shell commands:** `CODEMOD_STATE` and `STATE_OUTPUTS`, above.

What a step sets is saved with that step, so it is restored when the step is replayed on resume.

## Parameters

The default export receives `{ params, target, dryRun }`. Pass parameters with `--param key=value`.

```ts
export default async function main({ params }: { params: { team?: string } }) {
  const team = params.team ?? "all";
}
```

## Approvals

`await step(approval("Ship it?"))` asks before continuing.

- In an interactive terminal, you are asked directly. Answering **No** pauses the run.
- With `--no-interactive`, the run pauses at the approval and exits successfully.
- Continue a paused run with `codemod workflow resume --id <run-id> --approve`, or pass `--approve` to `workflow run` to approve everything up front.

## Runs

Every run is saved, with each step's result, so you can inspect and resume it:

```bash
npx codemod workflow list
npx codemod workflow status --id <run-id>
npx codemod workflow resume --id <run-id>
npx codemod workflow cancel --id <run-id>
```

Runs are stored under your data directory (`~/Library/Application Support/codemod/runs` on macOS). Set `CODEMOD_RUN_STORE_DIR` to store them elsewhere, or `CODEMOD_RUN_STORE=memory` to keep nothing. A dry run is never saved.

When a run ends early, the steps still running finish first and are recorded, so a resume does not repeat them:

- **A step fails:** the run ends as failed once the steps started alongside it are done.
- **A step waits for an approval** nobody can give: the run pauses there, also when the workflow catches the error. No step starts after it; resume with `--approve`.
- **The run is canceled** (Ctrl-C, `workflow cancel`, or the process being terminated): steps stop where they can (a shell command is terminated, file changes not yet written are dropped), and the run can be resumed.

## Installing codemod in a package

A codemod package can depend on `codemod` like any other tool it runs: package scripts and `npx codemod` then use that CLI, pinned to the version in `package.json`, and editors get its types for `codemod/workflow`, `codemod/ast-grep` and the other `codemod:*` modules, which always match that CLI. Packages created with `codemod init` are already set up. For an existing package:

```bash
npm install codemod
npm install --save-dev typescript
```

```json package.json
{
  "type": "module",
  "scripts": {
    "test": "codemod jssg test -l typescript ./scripts/codemod.ts",
    "validate": "codemod workflow validate -w workflow.ts"
  }
}
```

`npm install codemod` adds it under `dependencies`.

```json tsconfig.json
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "types": ["codemod"],
    "noEmit": true,
    "strict": true,
    "skipLibCheck": true
  }
}
```

Then `npx tsc` checks `workflow.ts` along with your transforms. Type-only imports are available as `codemod/main` (the `SgRoot`/`SgNode` types) and `codemod/langs/<language>`; `@codemod.com/jssg-types` still works and mirrors the same declarations.

- Step results are typed and read-only. `forEachFile` collects what the callback returns: returning `file.path` or `undefined` gives `outputs: readonly string[]`.
- A step result or callback return value that is not JSON is a type error, for example a `Set`, a `Map`, a `Date`, a function, or a `Promise` returned from an `async` callback.
- Type the default export's argument with `WorkflowContext`: `main({ params }: WorkflowContext<{ replacement?: string }>)`.
- Type `parse` with a language map: `parse<TS>(file)`, where `TS` is imported from `codemod/ast-grep/langs/typescript`.

The callback rules that depend on scope, such as assigning to an outside variable, are checked by `codemod workflow validate`, not by TypeScript.

## Validation

```bash
npx codemod workflow validate -w workflow.ts
```

Validation builds the workflow, which reports the callback rules above with their source positions.
