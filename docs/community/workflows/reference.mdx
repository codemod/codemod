A workflow is a TypeScript file, `workflow.ts`, whose default export runs **steps**. This page documents everything you can import from `codemod:workflow`.

## Complete example

```ts workflow.ts
import { step, forEachFile, parse, jssg, shell, approval } from "codemod:workflow";

const LEGACY = "moment";

export default async function main({ params }: { params: { replacement: string } }) {
  // Find the files that import the legacy library.
  const usages = await step("Find moment imports",
    forEachFile({ language: "typescript", containing: LEGACY }, (file) => {
      const root = parse(file);
      const found = root.root().findAll({ rule: { pattern: `import $X from "${LEGACY}"` } });
      return found.length ? file.path : undefined;
    }),
  );

  // Rewrite only those files.
  await step("Rewrite imports", forEachFile({ language: "typescript" }, (file) => {
    if (!usages.outputs.includes(file.path)) return;
    file.write(file.text.replaceAll(`from "${LEGACY}"`, `from "${params.replacement}"`));
  }));

  // Run an existing JSSG transform, then the formatter.
  await step("Apply transform", jssg("./scripts/codemod.ts", { include: "src/**/*.ts" }));
  await step(approval("Run the formatter?"));
  await step("Format", shell("npx prettier --write src"));
}
```

Run it with:

```bash
npx codemod workflow run -w . --param replacement=dayjs
```

## How a workflow runs

A workflow file contains three kinds of code, each with its own rules:

| Where | When it runs | Rule |
|---|---|---|
| Workflow body, outside any step | On every run and every resume | Deterministic; no file or network access |
| Inside a step | Once; its result is recorded | The result must be JSON-serializable |
| Inside a `forEachFile` callback | Once per file, in parallel, in isolated contexts | Outside variables arrive as frozen copies; changes go through the file object |

- **Steps are durable.** Each step's result is saved as soon as the step finishes. If a run fails or is canceled, `codemod workflow resume` replays the finished steps from their saved results and continues from the step that failed.
- **A step starts when you call `step()`.** `await` waits for it. `Promise.all([step(a), step(b)])` runs two steps at the same time.
- **Each step is identified by its order and content.** If you change a step that already finished and then resume, the run stops with a `NondeterminismError`, because the recorded result no longer matches. Changing the step that failed is fine; that is how you fix a run.

## `step(label?, task)`

Runs a task as a durable step and returns a promise for its result.

```ts
const result = await step("Rename files", forEachFile("src/**/*.less", (file) => {
  file.rename(file.path.replace(/\.less$/, ".css"));
}));
```

- **`label`** (optional): shown in progress output, `codemod workflow status` and errors. Defaults to a description of the task.
- **`task`**: `forEachFile(...)`, one of the [tasks](#tasks), or a function whose result should be computed once and recorded.
- **Result:** deeply frozen and read-only. Copy it before changing it.

```ts
const plan = await step("Plan batches", () =>
  usages.outputs.reduce((batches, path, index) => {
    (batches[index % 4] ??= []).push(path);
    return batches;
  }, [] as string[][]),
);
```

The workflow body and function steps have no file system or network access. Use a task such as `shell` for that.

## `forEachFile(selector, callback)`

Runs `callback` once per selected file and returns a task for `step()`.

### Selector

| Form | Example |
|---|---|
| A glob | `"src/**/*.less"` |
| A list of globs | `["**/*.ts", "**/*.tsx"]` |
| An object | `{ language: "tsx", exclude: "**/*.test.tsx", containing: "moment" }` |

Object fields:

| Field | Meaning |
|---|---|
| `include` | Glob or globs to select |
| `exclude` | Glob or globs to skip |
| `language` | Selects the language's file extensions when `include` is not set, and is the default language for `parse(file)` |
| `containing` | Only files whose text contains this string |

`.gitignore` is respected. A selector is plain data, so you can reuse and refine it: `{ ...sources, containing: "moment" }`.

### The file object

| Member | Meaning |
|---|---|
| `file.path` | Path relative to the target |
| `file.text` | Contents when the step started |
| `file.write(text)` | Replace the contents |
| `file.rename(path)` | Move the file |
| `file.delete()` | Remove the file |

Changes are recorded, not written immediately. When every file is done, the step checks for conflicts (for example, two files renamed to the same path) and applies all changes together. If there is a conflict, nothing is written.

### The callback

- Return a value to collect it; returned values become `result.outputs`, in path order. Return nothing to collect nothing.
- A callback that throws fails only that file; the error appears in `result.failures`.
- Callbacks must be synchronous.

### Result

```ts
{
  outputs: unknown[];
  changes: { written: string[]; renamed: { from: string; to: string }[]; deleted: string[] };
  failures: { path: string; error: string }[];
}
```

### Using outside variables

A callback runs in its own context, so the build copies in what it needs:

- **Module-level constants, functions and classes** it uses are copied into the callback.
- **Local variables of the surrounding function** are passed in as frozen copies when the step starts. They must be JSON values.
- **Imports** from `codemod:*` modules are available.

These are build errors, reported with the file, line and column:

- assigning to a variable declared outside the callback (return a value instead);
- using a local variable that is reassigned after it is declared;
- using a function or class declared inside the surrounding function (move it to module level);
- calling `step()` or another task inside the callback;
- passing a callback by name instead of writing it inline.

A local that is not JSON (a `Set`, a `Map`, a class instance) fails when the step starts, naming the variable.

## `parse(file, language?)`

Parses the file with [ast-grep](/community/jssg) and returns its root. Only available inside a `forEachFile` callback. The language comes from the argument, then the selector's `language`, then the file extension. Files you only rename are never parsed.

## Tasks

| Task | What it does |
|---|---|
| `jssg(path, options)` | Run a [JSSG](/community/jssg) transform file. Options: `include`, `exclude`, `basePath`, `files`, `language` (default `typescript`), `params`, `matrix`, `capabilities`, `semanticAnalysis`, `threads`, `dryRun`. Result: `{ changes, unmodified, failures }`. |
| `astGrep(path, options)` | Apply an ast-grep YAML rule file. Options: `include`, `exclude`, `basePath`, `threads`. |
| `shell(command, { env, cwd })` | Run a shell command. Result: `{ output }`. |
| `shard(options)` | Split files into groups. See [Sharding](/community/workflows/sharding). |
| `codemod(source, { params })` | Run another codemod package (registry name or local path) as part of this step. |
| `agent(prompt, options)` | Hand a prompt to a coding agent. Options: `systemPrompt`, `model`, `maxSteps`, `tools`. |
| `installSkill({ package, path, harness, scope, force })` | Install a package's agent skill. |
| `approval(message)` | Wait for a person to approve. See [Approvals](#approvals). |
| `branch(name)`, `commit(message, { add, allowEmpty })`, `pullRequest({ title, body, draft, base })` | Git automation. These only touch git when the run uses `--managed-git`; otherwise they are recorded as skipped. |

Paths given to `jssg`, `astGrep` and shard functions are relative to the workflow file.

### Shell commands

`shell` commands get these environment variables:

| Variable | Value |
|---|---|
| `CODEMOD_PATH` | The workflow's directory |
| `CODEMOD_STATE` | A file containing the workflow state as JSON |
| `CODEMOD_STATE_<KEY>` | Each state value, JSON-encoded |
| `STATE_OUTPUTS` | A file the command can write `key=value` (set) or `key@=value` (append) lines to; they become workflow state |

Shell commands, agents and skill installs are skipped in a dry run.

## State

Workflow state is a set of named JSON values shared by the workflow and the steps it runs.

```ts
import { step, shell, getState, setState } from "codemod:workflow";

setState("target", "react-19");
await step(shell('echo "version=19" >> "$STATE_OUTPUTS"'));
getState("version"); // 19
getState();          // { target: "react-19", version: 19 }
```

- **In the workflow:** `getState(key)` reads a value; `getState()` returns all of them. `setState(key, value)` sets one.
- **In JSSG transforms:** `setState`, `getState`, `unsetState` and `acquireLock` from `codemod:workflow`. See [Workflow context](/community/jssg/advanced/workflow).
- **In shell commands:** `CODEMOD_STATE` and `STATE_OUTPUTS`, above.

What a step sets is saved with that step, so it is restored when the step is replayed on resume.

## Parameters

The default export receives `{ params, target, dryRun }`. Pass parameters with `--param key=value`.

```ts
export default async function main({ params }: { params: { team?: string } }) {
  const team = params.team ?? "all";
}
```

## Approvals

`await step(approval("Ship it?"))` asks before continuing.

- In an interactive terminal, you are asked directly. Answering **No** pauses the run.
- With `--no-interactive`, the run pauses at the approval and exits successfully.
- Continue a paused run with `codemod workflow resume --id <run-id> --approve`, or pass `--approve` to `workflow run` to approve everything up front.

## Runs

Every run is saved, with each step's result, so you can inspect and resume it:

```bash
npx codemod workflow list
npx codemod workflow status --id <run-id>
npx codemod workflow resume --id <run-id>
npx codemod workflow cancel --id <run-id>
```

Runs are stored under your data directory (`~/Library/Application Support/codemod/runs` on macOS). Set `CODEMOD_RUN_STORE_DIR` to store them elsewhere, or `CODEMOD_RUN_STORE=memory` to keep nothing. A dry run is never saved.

## Validation

```bash
npx codemod workflow validate -w workflow.ts
```

Validation builds the workflow, which reports the callback rules above with their source positions.
