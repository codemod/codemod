The `shard` task splits a large migration into groups of files ("shards"), for example one per directory or per code owner. You then run the transform once per shard, typically opening one pull request each.

## How it works

1. A `shard` step finds the files the transform would change and groups them.
2. The workflow runs the transform for every shard, limited to that shard's files.

```ts workflow.ts
import { step, shard, jssg, approval, branch, commit, pullRequest, getState, setState } from "codemod/workflow";

export default async function main() {
  const shards = await step("Build shards", shard({
    method: { type: "directory", maxFilesPerShard: 20 },
    target: "./src",
    jssg: { path: "scripts/codemod.ts", language: "tsx", include: ["**/*.{ts,tsx}"] },
    previous: getState("shards"),
  }));
  setState("shards", shards);

  await Promise.all(shards.map(async (current, index) => {
    await step(approval(`Migrate ${current.name}?`));
    await step(branch(`codemod-migrate-${index}`));
    await step(`Migrate ${current.name}`, jssg("scripts/codemod.ts", {
      language: "tsx",
      files: current._meta_files,
    }));
    await step(commit(`refactor: migrate ${current.name}`));
    await step(pullRequest({ title: `refactor: migrate ${current.name}` }));
  }));
}
```

- **`previous: getState("shards")`** keeps assignments stable when the shard step runs again (see [Re-evaluation](#re-evaluation)).
- **`files: current._meta_files`** limits each transform run to its shard's files.
- `branch`, `commit` and `pullRequest` only touch git when the run uses `--managed-git`. See [Workflow Reference](/community/workflows/reference#tasks).

<Note>
In `workflow.yaml`, the same pattern is a `shard` step with `output_state`, followed by a matrix node with `from_state`. See the [workflow.yaml reference](/community/workflows/yaml).
</Note>

## File discovery

Files are filtered before they reach any shard method:

- With `jssg`, the transform runs in dry-run mode on the files matching its `include` under `target`, and only files it would change are kept. If it changes none, files its selector matches are used instead.
- Without `jssg`, every file matching `filePattern` under `target` is eligible.

<ParamField path="target" type="string" default=".">
  Directory to scan, relative to the run's target.
</ParamField>

<ParamField path="filePattern" type="string">
  Glob for eligible files when `jssg` is not set.
</ParamField>

<ParamField path="jssg" type="object">
  A JSSG transform used to pre-filter files: `path` plus the [`jssg` task options](/community/workflows/reference#tasks).
</ParamField>

<ParamField path="previous" type="array">
  The result of an earlier run of this shard step, for incremental re-evaluation.
</ParamField>

## Built-in methods

### Directory

Groups files by their immediate subdirectory under `target`, then bin-packs them.

```ts
shard({ method: { type: "directory", maxFilesPerShard: 20, minShardSize: 5 }, target: "./src", filePattern: "**/*.tsx" })
```

Each shard has `name` (`"{directory}-{index}"`, for example `"components-0"`), `directory` and `_meta_files`.

### Codeowner

Groups files by their owning team from `.github/CODEOWNERS` (or a root `CODEOWNERS`), then bin-packs them.

```ts
shard({ method: { type: "codeowner", maxFilesPerShard: 30 }, target: "./src", filePattern: "**/*.tsx" })
```

Each shard has `name` (`"{team}-{index}"`, for example `"platform-team-0"`), `team` and `_meta_files`.

### Method options

<ParamField path="method.type" type="string" required>
  `directory` or `codeowner`.
</ParamField>

<ParamField path="method.maxFilesPerShard" type="number" required>
  Target number of files per shard.
</ParamField>

<ParamField path="method.minShardSize" type="number">
  Trailing shards smaller than this are merged into the previous shard.
</ParamField>

## Custom shard functions

For grouping that the built-in methods can't express, such as dependency-aware clustering, point `method.function` at a JS/TS file. It receives the pre-filtered file list and returns the shards; the engine handles file selection.

```ts
shard({
  method: { function: "scripts/shard-by-deps.ts" },
  target: "./src",
  jssg: { path: "scripts/codemod.ts", language: "tsx", include: ["**/*.{ts,tsx}"] },
})
```

```ts scripts/shard-by-deps.ts
import { parse } from "codemod/ast-grep";
import type { ShardInput, ShardResult } from "codemod/workflow";

export default function shard(input: ShardInput): ShardResult[] {
  const { files, targetDir, previousShards } = input;
  // Group files, for example by connected components of their imports.
  return [{ name: "shard-0", _meta_shard: 0, _meta_files: files }];
}
```

### ShardInput

| Field | Type | Description |
|-------|------|-------------|
| `files` | `string[]` | Relative paths of eligible files |
| `targetDir` | `string` | Absolute path of the target directory |
| `previousShards` | `ShardResult[]` | The `previous` value passed to the shard step |

### ShardResult

| Field | Type | Description |
|-------|------|-------------|
| `name` | `string` | Shard identifier, for labels, branch names and PR titles |
| `_meta_shard` | `number` | Shard index |
| `_meta_files` | `string[]` | Files in this shard |
| Any other key | `unknown` | Available on the shard object in your workflow |

## Re-evaluation

When the repository changes, run the shard step again with `previous` set to the earlier result. Evaluation is incremental:

- **Existing assignments are kept**: a file already in shard 1 stays in shard 1.
- **New files go to new shards**, never into existing ones.
- **Shards whose files were all deleted are dropped.**

Custom shard functions receive the same value as `previousShards` and can implement their own incremental logic.

## Shipping plain and sharded variants in one package

A package can ship several workflow files through `codemod.yaml`'s `workflows:` list, for example `workflow.ts` and `workflows/sharded.ts`. Users pick one in the CLI or when creating a Campaign. See [Multiple workflows per package](/community/package-structure#multiple-workflows-per-package).
