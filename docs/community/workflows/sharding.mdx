The `shard` task splits a large migration into groups of files ("shards"), for example one per directory or per code owner. You then run the migration once per shard, typically opening one pull request each.

## How it works

1. A `shard` step finds the files the codemod would change and groups them.
2. The workflow runs the codemod for every shard, limited to that shard's files, one shard at a time when each gets its own branch and pull request.

```ts workflow.ts
import { step, shard, forEachFile, approval } from "codemod/workflow";
import { branch, commit, pullRequest } from "codemod/git";
import migrate from "./scripts/migrate.ts";
import wouldChange from "./scripts/would-change.ts";

export default async function main() {
  const shards = await step("Build shards", shard({
    method: { type: "directory", maxFilesPerShard: 20 },
    target: "./src",
    files: { include: "**/*.{ts,tsx}", language: "tsx" },
    filter: wouldChange,
  }));

  // One shard at a time: git steps share one checkout.
  for (const [index, current] of shards.entries()) {
    await step(approval(`Migrate ${current.name}?`));
    await step(branch(`codemod-migrate-${index}`));
    await step(`Migrate ${current.name}`, forEachFile(
      { include: current._meta_files, language: "tsx" },
      migrate,
    ));
    await step(commit(`refactor: migrate ${current.name}`));
    await step(pullRequest({ title: `refactor: migrate ${current.name}` }));
  }
}
```

- **`previous`** (not used here) takes an earlier result, to keep assignments stable when shards are evaluated again (see [Re-evaluation](#re-evaluation)).
- **`filter`** keeps the files it returns `true` for: here, those the migration would change (`wouldChange` can call the same helpers `migrate` does, without writing). It is a `forEachFile` callback, written inline or imported; what it does to a file is not kept.
- **`include: current._meta_files`** limits each run of the migration to its shard's files.
- `branch`, `commit` and `pullRequest` come from `codemod/git` and only touch git when the run uses `--managed-git`. See [Git steps](/community/workflows/reference#git-steps).

<Warning>
Don't run shards that use git steps at the same time, for example with `Promise.all`. Git steps share the run's one checkout, so one shard could commit on another shard's branch. A git step started while other steps are still running fails with "managed git steps can't run in parallel", with or without `--managed-git`. Shards without git steps can still run in parallel. Separate checkouts per shard are planned as an explicit API.
</Warning>

<Note>
In `workflow.yaml`, the same pattern is a `shard` step with `output_state`, followed by a matrix node with `from_state`. A matrix node with `branch_name`, `pull_request` or a step `commit` runs its values one at a time. See the [workflow.yaml reference](/community/workflows/yaml).
</Note>

## File discovery

Files are chosen before they reach any shard method:

- `files` selects the eligible files under `target`: a glob, a list of globs, or `{ include, exclude, language }`. Without it, the files of the package's `targets.languages`.
- `filter`, when given, runs on each of them, in isolates, and keeps those it returns `true` for. If it throws on every file, the shard step fails.
- A built-in method given neither `files` nor `filter` takes every file under `target`.

<ParamField path="target" type="string" default=".">
  Directory to scan, relative to the run's target.
</ParamField>

<ParamField path="files" type="string | string[] | object">
  The eligible files under `target`, as a glob, globs, or `{ include, exclude, language }`.
</ParamField>

<ParamField path="filter" type="function">
  A `forEachFile` callback, inline or imported, that returns `true` for the files to keep.
</ParamField>

<ParamField path="previous" type="array">
  The result of an earlier run of this shard step, for incremental re-evaluation.
</ParamField>

## Built-in methods

### Directory

Groups files by their immediate subdirectory under `target`, then bin-packs them.

```ts
shard({ method: { type: "directory", maxFilesPerShard: 20, minShardSize: 5 }, target: "./src", files: "**/*.tsx" })
```

Each shard has `name` (`"{directory}-{index}"`, for example `"components-0"`), `directory` and `_meta_files`.

### Codeowner

Groups files by their owning team from `.github/CODEOWNERS` (or a root `CODEOWNERS`), then bin-packs them.

```ts
shard({ method: { type: "codeowner", maxFilesPerShard: 30 }, target: "./src", files: "**/*.tsx" })
```

Each shard has `name` (`"{team}-{index}"`, for example `"platform-team-0"`), `team` and `_meta_files`.

### Method options

<ParamField path="method.type" type="string" required>
  `directory` or `codeowner`.
</ParamField>

<ParamField path="method.maxFilesPerShard" type="number" required>
  Target number of files per shard.
</ParamField>

<ParamField path="method.minShardSize" type="number">
  Trailing shards smaller than this are merged into the previous shard.
</ParamField>

## Custom shard functions

For grouping that the built-in methods can't express, such as dependency-aware clustering, give a shard function as `method.function`: written inline, or imported from a file whose default export it is. It receives the chosen files and returns the shards; the engine handles file selection. Like a callback, it runs in its own isolate, the workflow body never loads its file, and publishing includes it.

```ts
import shardByDeps from "./scripts/shard-by-deps.ts";
import wouldChange from "./scripts/would-change.ts";

shard({
  method: { function: shardByDeps },
  target: "./src",
  files: { include: "**/*.{ts,tsx}", language: "tsx" },
  filter: wouldChange,
})
```

Write `shard`'s options and its `method` inline, as objects, so the build can find the functions in them. A file path where a function goes is a build error, and so are the removed `jssg` and `filePattern` options (use `filter` and `files`).

```ts scripts/shard-by-deps.ts
import { parse } from "codemod/ast-grep";
import type { ShardInput, ShardResult } from "codemod/workflow";

export default function shard(input: ShardInput): ShardResult[] {
  const { files, targetDir, previousShards } = input;
  // Group files, for example by connected components of their imports.
  return [{ name: "shard-0", _meta_shard: 0, _meta_files: files }];
}
```

### ShardInput

| Field | Type | Description |
|-------|------|-------------|
| `files` | `string[]` | Relative paths of eligible files |
| `targetDir` | `string` | Absolute path of the target directory |
| `previousShards` | `ShardResult[]` | The `previous` value passed to the shard step |

### ShardResult

| Field | Type | Description |
|-------|------|-------------|
| `name` | `string` | Shard identifier, for labels, branch names and PR titles |
| `_meta_shard` | `number` | Shard index |
| `_meta_files` | `string[]` | Files in this shard |
| Any other key | `unknown` | Available on the shard object in your workflow |

## Re-evaluation

When the repository changes, run the shard step again with `previous` set to the earlier result. Evaluation is incremental:

- **Existing assignments are kept**: a file already in shard 1 stays in shard 1.
- **New files go to new shards**, never into existing ones.
- **Shards whose files were all deleted are dropped.**

Custom shard functions receive the same value as `previousShards` and can implement their own incremental logic.

## Shipping plain and sharded variants in one package

A package can ship several workflow files through `codemod.yaml`'s `workflows:` list, for example `workflow.ts` and `workflows/sharded.ts`. Users pick one in the CLI or when creating a Campaign. See [Multiple workflows per package](/community/package-structure#multiple-workflows-per-package).
