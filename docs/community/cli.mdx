## Command Relationships

The Codemod CLI provides different commands for different stages of development:

### High-Level Commands (Production)
```bash
# Run a published package from the registry
npx codemod @org/my-package

# Run a local workflow package
npx codemod workflow run -w ./my-package/
```
**Use for**: Production codemods, multi-step workflows, parameterized transforms

### Quick Testing Commands (Development)
```bash
# Test a jssg transform directly
npx codemod jssg run ./transform.ts ./src --language tsx

# Test jssg transform with fixtures
npx codemod jssg test ./transform.ts --language tsx
```
**Use for**: Rapid iteration, testing patterns, development

### Package Lifecycle
```bash
# Scaffold a new package
npx codemod init

# Validate workflow
npx codemod workflow validate -w workflow.ts

# Publish to registry
npx codemod publish
```

<Info>
  **When to use what**: Use `codemod workflow run` for orchestrated, multi-step transformations with parameters. Use `codemod jssg run` for quick testing of a single jssg transform during development.
</Info>

## Telemetry

When analytics are enabled, the CLI sends product telemetry to PostHog (and a separate Scarf
gateway for install/usage signals). Logged-in users are keyed by their Codemod account id.
Anonymous installs use a local telemetry id and are never aliased to an account.

For logged-in sessions only, the CLI may also send a separate PostHog `$set` with the account
**email** so dashboards can show people instead of raw UUIDs. That update is PostHog-only (not
Scarf), deduped locally, and skipped when you opt out.

The first interactive run shows a one-line notice about telemetry. The CLI remembers that
it showed the notice. It does not show the notice in CI, without a terminal, with
`--no-interactive`, or in JSONL and `--control` mode.

Use `codemod telemetry off` to opt out on this installation. Check your effective setting
with `codemod telemetry status`, or restore the default with `codemod telemetry on`.

Disable all of this for a single invocation with `--disable-analytics`, or by setting
`DISABLE_ANALYTICS=true` / `DISABLE_ANALYTICS=1` in the environment. `DO_NOT_TRACK=1` (any value but empty, `0` or `false`) does the same. The flag works on explicit
commands and on implicit package runs such as `npx codemod @org/package --disable-analytics`.
These overrides still apply after `codemod telemetry on`.

More detail: [Telemetry compliance](https://codemod.com/telemetry-compliance).

# CLI Command Reference

Codemod CLI is accessible using the `npx codemod` command. The following commands and options are available:

### `codemod ai`

<Experimental />

<Info>
  In an interactive terminal, bare `npx codemod` opens a launcher. In npm-based usage, that launcher refreshes to the latest published CLI before prompting you to create a package or run one from the registry. In non-interactive contexts, the CLI prints next steps and exits with status `1`.
</Info>

Manage Master Codemod Skill (MCS) lifecycle for supported harnesses.

**`ai`**

Install the `codemod` MCS skill package, configure Codemod MCP, and install the universal `/codemod` entrypoint where the harness supports it.

```bash
npx codemod ai [--harness <claude|goose|opencode|cursor|codex|auto>] [--project|--user] [--force] [--no-interactive] [--update-policy <manual|notify|auto-safe>] [--update-source <local|registry|URL>] [--require-signed-manifest|--allow-unsigned-manifest] [--format <logs|table|json|yaml>]
```

Interactive prompts are enabled by default in TTY sessions. Use `--no-interactive` to skip prompts and use flags/defaults directly.

With `--harness auto` (the default), install first checks whether it is running inside a coding agent (Claude Code, Codex, Cursor, OpenCode, Goose or Antigravity) and sets up that agent. Otherwise it looks for an agent folder or config file in the project, such as `.claude`, `.cursor`, `.codex` or `opencode.json`, and prefers Claude Code when it finds several. If it finds neither, it sets up Claude Code and warns, so pass `--harness` to choose another agent. The output says which agent was set up and why, marks files that a re-run left unchanged as up to date, and ends with numbered next steps for that agent, such as approving the MCP server in Claude Code or trusting the folder in Codex.

Along with skill files, install writes or updates a Codemod MCP server entry. Project installs (`--project`) write a portable launcher pinned to the CLI version that ran the install, so the config can be committed and used on other machines and checkouts:

```json
{
  "mcpServers": {
    "codemod": {
      "command": "npx",
      "args": ["-y", "codemod@<installing CLI version>", "mcp"]
    }
  }
}
```

User installs (`--user`) stay on the current machine, so they launch the installed `codemod` executable directly. If the CLI itself was run through `npx`, its cached executable is temporary, so user installs fall back to `codemod` on `PATH` (outside the npx cache) or the same pinned `npx` launcher. Re-running `ai --project` repairs one known broken entry without `--force`: a project entry whose command is an absolute path to an executable inside npm's npx cache (`_npx`), which earlier releases wrote. Every other existing `codemod` entry is kept and reported as a conflict, including absolute paths outside the npx cache, older pinned `codemod@<version>` launchers, and all user-scope entries. Re-run with `--force` to replace it.

Prerequisites for project installs:
- The project MCP launcher needs Node.js and npm (`npx`) on every machine that uses the committed config. The first launch of a pinned version downloads it from the npm registry unless it is already in the npm cache.
- If npm is not available, use `--user` with an installed `codemod` executable instead.
- The Claude periodic update hook runs a POSIX shell script. Claude Code runs hook commands with `sh` on macOS and Linux and with Git Bash on Windows, so Windows machines need Git for Windows; the hook does not run under PowerShell.

For Opencode, install writes `opencode.json` using the Opencode-specific `mcp` schema instead of `mcpServers`.

MCP config paths by harness and scope:
- `claude`: `./.mcp.json` (project), `~/.claude.json` (user, the same file `claude mcp add -s user` writes; other keys in it are kept)
- `goose`: `./.goose/mcp.json` (project), `~/.config/goose/mcp.json` (user)
- `opencode`: `./opencode.json` (project), `~/.config/opencode/opencode.json` (user)
- `cursor`: `./.cursor/mcp.json` (project), `~/.cursor/mcp.json` (user)
- `codex` (CLI + macOS app): `./.codex/config.toml` (project), `~/.codex/config.toml` (user) under `[mcp_servers.codemod]`

If a conflicting Codemod MCP entry already exists, re-run with `--force` to overwrite it. For Opencode, Codemod leaves any legacy `./.opencode/mcp.json` or `~/.opencode/mcp.json` file in place to avoid deleting unrelated MCP servers.

`ai` also upserts a managed Codemod discovery section in harness discovery guides (project root for `--project`, home directory for `--user`) without duplicating entries:
- `claude`: `CLAUDE.md`
- `goose`: `AGENTS.md` and `.goosehints`
- `cursor`: `AGENTS.md`
- `opencode`: `AGENTS.md`
- `codex`: `AGENTS.md`
`ai` also installs `/codemod` where the harness has a native command or workflow file surface:
- `claude`: `./.claude/commands/codemod.md` (project), `~/.claude/commands/codemod.md` (user)
- `goose`: `~/.config/goose/recipes/codemod.yaml` + `~/.config/goose/config.yaml` registration (user only)
- `opencode`: `./.opencode/commands/codemod.md` (project), `~/.config/opencode/commands/codemod.md` (user)
- `cursor`: `./.cursor/commands/codemod.md` (project), `~/.cursor/commands/codemod.md` (user)
The installed `/codemod` command routes by intent:
- create, scaffold, or refine codemods -> codemod authoring flow
- search, run, or apply existing codemods -> registry discovery and execution flow

The generated Codemod skill package includes these authored files:
- `SKILL.md`: the main skill instructions and Codemod-specific authoring and execution defaults
- `agents/openai.yaml`: the Codemod agent interface definition used by compatible harnesses
- `commands/codemod.md`: the `/codemod` command routing rules for harnesses with a native command surface

The installed skill also points users to CLI fallbacks when MCP is unavailable or blocked. The main user-reproducible commands are:
- `npx codemod ai docs`: list docs resources exposed through the CLI
- `npx codemod ai docs <resource-id>`: read a specific docs resource such as `codemod-cli`, `codemod-creation-workflow`, or `codemod-troubleshooting`
- `npx codemod ai dump-ast <file>` or `npx codemod ai dump-ast --`: inspect AST shape for a file or stdin
- `npx codemod ai node-types <language>`: inspect tree-sitter node kinds for a language
- `npx codemod ai call validate_codemod_package --input '{"package_path":"."}'`: validate whether a codemod package still contains starter scaffold markers or other package-surface issues
- `npx codemod ai feedback --category <category> --message <message>`: submit short anonymous platform feedback after consent is recorded

`ai` also wires a periodic, cooldown-protected update check trigger:
- `claude`: `hooks.SessionStart` command in `./.claude/settings.json` (project) or `~/.claude/settings.json` (user). The project hook runs `"$CLAUDE_PROJECT_DIR"/.claude/codemod/periodic-update/check-updates.sh`, so it keeps working after the project is cloned or moved. Re-running `ai` replaces a project hook that an earlier install wrote with an absolute runner path, including one written from a different checkout.
  Only unmodified generated hooks with an unambiguous absolute runner command are migrated automatically. Commands containing whitespace (including old unquoted paths with spaces), quoting, arguments or shell syntax are preserved, as are hooks with custom matchers, timeouts or other fields. Review and remove obsolete preserved hooks manually when moving a checkout; install adds the portable hook without deleting those commands.
- `cursor`: `hooks.afterAgentResponse` command in `./.cursor/hooks.json` (project) or `~/.cursor/hooks.json` (user)
- `opencode`: plugin `codemod-periodic-update.js` in `./.opencode/plugins/` (project) or `~/.config/opencode/plugins/` (user), listening to `session.idle`
- `goose`: managed `codemod-periodic-update` block in `./.goosehints` (project) or `~/.config/goose/.goosehints` (user) as fallback guidance
- `codex`: `notify = ["sh", "<runner>"]` in `./.codex/config.toml` (project) or `~/.codex/config.toml` (user)
Managed update policy is install-flag driven and shared by install-time reconciliation and periodic checks:
- `--update-policy <manual|notify|auto-safe>` (default: `auto-safe`)
- `--update-source <local|registry|URL>` (default: `registry`)
- `--require-signed-manifest` or `--allow-unsigned-manifest` (optional override)
  `--update-source` only accepts `local`, `registry`, or an absolute `http(s)` URL (legacy `registry:`/`url:` aliases are rejected).
Project periodic runners use the same pinned `npx -y codemod@<installing CLI version>` launcher as project MCP, even when another global CLI version is installed. User runners retain their local executable/PATH fallback. Periodic runs enforce signed manifest verification via `--require-signed-manifest` in the generated runner command.
After install, restart or reload your harness session so newly installed skills and command entrypoints are picked up.

**`ai feedback`**

Submit short anonymous platform feedback for Codemod AI, MCP, JSSG, workflows, docs, CLI, registry, or related surfaces. The command records anonymous feedback consent in the user-wide Codemod config, including the timestamp at which this OS user allowed feedback submission.

```bash
npx codemod ai feedback --category <category> --message <message>
```

Recommended categories are `jssg`, `workflow`, `ai-docs`, `mcp`, `cli`, `registry`, `package-validation`, and `other`.

Examples:

```bash
npx codemod ai feedback --category jssg --message "I wish JSSG had clearer examples for multi-file transforms."
npx codemod ai feedback --category ai-docs --message "The docs resource for runtime capabilities should explain which Node APIs are unavailable."
```

Feedback is anonymous. Do not include source code, secrets, auth tokens, private repository paths, user identity, or long transcripts in the message.

**`ai update`**

Run managed update reconciliation/apply through CLI (same policy engine used by periodic hooks).

```bash
npx codemod ai update [--harness <claude|goose|opencode|cursor|codex|auto>] [--project|--user] [--force] [--no-interactive] [--update-policy <manual|notify|auto-safe>] [--update-source <local|registry|URL>] [--require-signed-manifest|--allow-unsigned-manifest] [--format <logs|table|json|yaml>]
```

If managed install state is missing, `ai update` automatically falls back to an install flow and then applies update reconciliation.

`ai` performs internal skill validation checks during install flow.

**`ai list`**

List installed Codemod skills for a harness.

```bash
npx codemod ai list [--harness <claude|goose|opencode|cursor|codex|auto>] [--format <logs|table|json|yaml>]
```

Use this command to inspect which Codemod-managed skills are already installed for a given harness before running `codemod ai` again or troubleshooting harness setup.

**`ai dump-ast`**

Dump AST nodes for a source file or stdin using the same parser surface exposed through Codemod MCP.

```bash
npx codemod ai dump-ast [FILE] [--language <language>] [--json]
```

- Omit `FILE` or pass `-` to read from stdin.
- If you do not pass `--language`, the CLI infers it from the file extension when possible and otherwise defaults to `tsx` for stdin.

```bash
# Parse a file and print AST text
npx codemod ai dump-ast ./src/component.tsx

# Parse stdin as TypeScript and emit JSON
cat ./src/index.ts | npx codemod ai dump-ast - --language typescript --json
```

**`ai node-types`**

Print tree-sitter node types for a supported language.

```bash
npx codemod ai node-types <language> [--json]
```

```bash
npx codemod ai node-types tsx
npx codemod ai node-types python --json
```

**`ai docs`**

List, read, or search Codemod AI documentation resources from the CLI.

```bash
npx codemod ai docs [query...] [--json]
```

- Run without a query to list available docs-backed resources.
- Pass a resource name or URI to read it.
- Pass a search phrase to search across available resources.

```bash
# List available docs resources

npx codemod ai docs codemod-cli-instructions
```

Inspect MCP-equivalent tools exposed by the CLI.

```bash
npx codemod ai tools [--json]
```

- `ai tools` lists available tool names and descriptions.
- `ai tool <name>` prints metadata and the JSON input schema for a single tool.

**`ai call`**

Call an MCP-equivalent tool directly from the CLI with JSON input.


- Use `--input @request.json` to load input from a file.
- Use `--input -` to read JSON input from stdin.

```bash
npx codemod ai call dump_ast --input '{"language":"tsx","source":"const x = 1;"}'
```

Inspect and read MCP-equivalent resources exposed by the CLI.

```bash
npx codemod ai resources [--json]
npx codemod ai resource <uri-or-name> [--json]
```

- `ai resources` lists the available resource names and URIs.
- `ai resource` reads one resource by URI or resource name.

### Package skill install (prompted from package run)

<Experimental />

Install a package skill from registry metadata into harness skill paths.
The installer copies the authored skill directory recursively from the package (`agents/skill/<skill-name>/`), including any additional files you add (for example extra `.md` references).
This flow also updates managed Codemod discovery hints in harness discovery guides (`CLAUDE.md` for Claude, `AGENTS.md` and `.goosehints` for Goose, `AGENTS.md` for Cursor/OpenCode/Codex) without duplication, then prompts you to restart/reload the harness session.

```bash
npx codemod <package-id>
```

In interactive TTY sessions, `npx codemod <package-id>` prompts for harness/scope/overwrite when installable skill behavior is available.

<Info>
  Behavior-aware package runtime:

  - **Workflow-only package**: `npx codemod <package-id>` runs the workflow behavior.
  - **Skill-only package**: `npx codemod <package-id>` does not run a no-op workflow. It returns install guidance and, in interactive terminals, can prompt to install the skill.
  - **Workflow + skill package**: `npx codemod <package-id>` runs workflow behavior and can optionally prompt to install skill behavior after run completion.
  - **Multi-workflow package**: when the package's `codemod.yaml` declares multiple workflows under `workflows:`, the default workflow runs unless you pass `--workflow <name>`. In an interactive terminal with no flag, the CLI shows a picker.
</Info>

**AI-native error codes**

| Code | Exit | Meaning |
| --- | --- | --- |
| `E_SKILL_PACKAGE_NOT_FOUND` | `27` | Unknown package id / unresolved package version |
| `E_SKILL_PACKAGE_INSTALL_FAILED` | `28` | Registry resolution, metadata parse, or install write failure |

Example machine-readable failure (`--format json`):

```json
{
  "ok": false,
  "code": "E_SKILL_PACKAGE_NOT_FOUND",
  "exit_code": 27,
  "message": "Unknown skill package id: jest-to-vitestx",
  "hint": "Run `codemod search <migration> --format json` to locate a valid package id."
}
```

### `codemod workflow`

Manage and execute [Codemod packages](/community/package-structure).

A Codemod package is a directory containing `workflow.ts` (or a legacy `workflow.yaml`) and transformation scripts. Workflows run durable steps using different engines (jssg, YAML ast-grep, shell commands, AI agents, etc.); every step is recorded so a run can be resumed.

**When to use**:
- ✅ Production codemods with multiple steps
- ✅ Parameterized transformations
- ✅ Multi-repo orchestration
- ✅ Resuming long migrations

**Learn more**: [Workflow Reference](/community/workflows/reference)

**`workflow run`**

Run a complete Codemod package.

- Use `npx codemod workflow run -w <path>` for local Codemod packages and directories
- Use `npx codemod <package-name>` to run packages directly from the [Codemod Registry](https://app.codemod.com/registry)

<CodeGroup>

```bash Running a local workflow
npx codemod workflow run -w <workflow.ts|workflow.yaml|directory>
```

```bash Running a workflow from Codemod Registry
npx codemod <package-name>
```

</CodeGroup>

A registry run (`npx codemod <package-name>`, or `npx codemod run <package-name>`) takes the same run flags as `workflow run`: `--target`, `--param`, `--dry-run`, `--approve`, `--managed-git`, `--allow-dirty`, `--allow-ai`, `--no-interactive`, `--install-skill`, `--agent`, `--model` and `--format`. It picks one of the package's workflows with `--workflow <NAME>` instead of `--workflow-name`.

Package runs use the 2.0 engine by default. `codemod run --v1 <package>` (or `CODEMOD_V1=on`) is a deprecated [opt-in fallback to codemod 1.18.7](/community/workflows/migrate#running-a-package-with-codemod-1x) for eligible 1.x YAML packages.

<ResponseField name="-w, --workflow <PATH>" type="string" required>
  Path to a workflow file or a package directory. In a directory, the workflow declared in `codemod.yaml` runs, otherwise `workflow.ts`, otherwise `workflow.yaml`.
</ResponseField>

<ResponseField name="--dry-run" type="boolean">
  Run every step without changing files. Later steps see what earlier steps would have changed, and the run ends by printing the diff of all of it (`run_diff` events with `--format jsonl`). Shell commands, HTTP requests (unless the step sets `dryRun: "perform"`), agents and skill installs are skipped, and the run is not saved.
</ResponseField>

<ResponseField name="--allow-dirty" type="boolean">
  Let the run change a target that has uncommitted changes, or that is not in a git repository. Without it, the run checks just before it first changes the target: before a step writes, renames or deletes a file, and before a `shell`, `agent` or `installSkill` step, or a git step with `--managed-git`. An interactive run asks; an unattended one fails that step and writes nothing. A run that only reads (a check or a report) is never stopped by uncommitted changes. Dry runs are not checked. `workflow resume` checks only a run that stopped before it first wrote (the changes a run made itself don't count); `workflow resume --allow-dirty` skips that.
</ResponseField>

<ResponseField name="--approve" type="boolean">
  Give every approval the workflow asks for: `approval(...)` steps and manual nodes in `workflow.yaml`, and the steps that run or send something (shell commands, coding agents, HTTP requests, pull requests). Give only some kinds with `--approve=shell,http` (written with `=`; the kinds are `shell`, `agent`, `http`, `pull-request` and `approval`).

  Without it, a run nobody can answer for pauses at the first `approval(...)` and can be continued with `workflow resume --approve`. What its steps run and send depends on whose workflow it is: your own (`workflow run -w <file>`, `codemod run ./local-dir`) goes ahead; a registry package's shell, agent, HTTP and pull request steps fail without running, as do those of a registry package your workflow nests. Read what a package runs before you approve it: its commands get the job's permissions and environment.

  ```bash
  npx codemod workflow run -w ./my-codemod --approve --no-interactive
  npx codemod @org/my-package@1.2.0 --approve --no-interactive
  ```
</ResponseField>

<ResponseField name="--allow-ai" type="boolean">
  <Experimental />

  Let `assess()` from [`codemod/assess`](/community/workflows/reference#assessing-files-with-codemod%2Fassess) send files to the decision model (System One unless configured otherwise). Without it, an interactive run asks before any step runs, and an unattended run that imports `codemod/assess` fails at once. The provider's key comes from the environment (`TYPESAFE_API_KEY`, `OPENAI_API_KEY`); an interactive run without one asks for a key to use for that run only. `workflow resume` checks both again.
</ResponseField>

<ResponseField name="--agent <ID>" type="string">
  <Experimental />

  The coding agent `agent(...)` steps use (`claude-code`, `codex`, ...). Defaults to the one saved in the launcher; without either, an interactive run asks when a step needs one.
</ResponseField>

<ResponseField name="--model <PROVIDER/MODEL>" type="string">
  <Experimental />

  The decision model `assess()` uses, e.g. `openai/gpt-6-luna`; a bare model name is System One's (`systemone/jev-latest`). It comes before the model saved in the launcher (`"decisionModel"` in the CLI's `config.json`) and the `DECISION_PROVIDER` / `DECISION_MODEL` variables; a `decision_model` in the package's `codemod.yaml`, or a model named in the `assess()` call, still comes first.
</ResponseField>

**The launcher (opt-in)**

<Experimental />

By default a run in a terminal prints plain lines and asks with plain prompts. With `CODEMOD_LAUNCHER=1`, `workflow run`, `codemod <package>` and `workflow resume` open a full-screen terminal UI instead. A new run starts on a setup screen (target, dry run, params, coding agent, decision model; your agent and model are saved for next time); then the screen shows the run's steps, logs and diffs, with approvals answered in place (`y` approves, `n` rejects, which ends the run, and `l` stops it there to resume later). After a dry run, `a` runs it for real. Even with `CODEMOD_LAUNCHER=1` it does not open with `--no-interactive`, `--format jsonl`, in CI, or when input or output is piped; those runs print the plain output.

A run is unattended when you pass `--no-interactive`, when there is no terminal to ask on (input piped in), and when the `CI` environment variable is set (to anything but empty, `0` or `false`). When the CLI does ask, pressing Enter answers no: every question is about running or publishing something. See [Running in CI and from agents](/community/workflows/ci-and-agents).

<ResponseField name="--managed-git" type="boolean">
  <Experimental />

  Let `branch`, `commit` and `pullRequest` steps (or `branch_name`, `commit` and `pull_request` in `workflow.yaml`) change the repository. Without it, those steps are recorded as skipped.
</ResponseField>

<ResponseField name="--format <text|jsonl>" type="string">
  `jsonl` prints one JSON object per engine event (`run_started`, `step_started`, `step_progress`, `step_log`, `step_retrying`, `step_finished`, `run_finished`, ...) on stdout. `run_finished` has the run's `status`, its `error`, `failed_files` (how many files failed in all), and `partial_steps`: each step some files failed in, with its `position`, `label`, `failed_files` and `files` (how many it ran on).

  If a `forEachFile` callback or a legacy `js-ast-grep` transform module cannot load, the step fails and its selected files count as failed. Legacy `js-ast-grep` also reports malformed JavaScript or TypeScript input as a file failure, not as an unchanged file.

  It also has `output`, what the workflow returned (or gave [`fail()`](/community/workflows/reference#failing-a-run-with-a-report)), dry runs included, and `steps`: every recorded step with its `position`, `label`, `status` and `result`. An `output` over 1 MiB as JSON is `null`, with `output_omitted: { bytes, limit }`; step results share another 1 MiB, and one that does not fit is `null` with `result_omitted`. A saved run has all of it in `workflow status --id <ID> --format json`.

  ```json
  {"event":"run_finished","run_id":"…","status":"failed","error":"1 check failed","failed_files":0,"partial_steps":[],
   "output":{"checks":[{"id":"no-var","status":"fail"}]},
   "steps":[{"position":0,"label":"Find var","status":"succeeded","result":{"outputs":["src/a.ts"]}}],"seq":5,"ts":"…"}
  ```

  Every event has `seq`, which counts up through the whole run, also across `workflow resume`, and `ts`. Step events carry `step`, the step's key (its position, or `"3/0"` for step 0 of the codemod that step 3 runs), and `parent` (`"3"` there, else `null`); `step_started` and `step_finished` also carry the step's `kind` (`forEachFile`, `approval`, `shell`, ...). `run_started` echoes the run's `target`, `params`, `dry_run` and `settings`. `run_log` (the workflow body's `console` output) has the `step` of the nested codemod it came from, or `null`. A real run reports each file a step changes as a `step_diff` event (`path`, `diff`, `additions`, `deletions`; a diff over 256 KiB is left out, with `diff_omitted`); a dry run reports `run_diff` at the end instead. The TypeScript types are in `codemod/protocol`; see [Drive codemod from a program](/community/workflows/control).

  In text format, a run that returned something ends with `Output: <JSON>`, cut at 200 characters.

  Experimental API notices go to stderr in text mode and appear as `experimental` events with an `api` field in JSONL mode. They are not part of `output`.
</ResponseField>

#### Exit codes

`workflow run`, `workflow resume` and `codemod <package>` exit with:

| Code | Meaning |
| ---- | ------- |
| `0` | The run finished. |
| `1` | The run failed, was paused (Ctrl-C), canceled, or rejected at an approval. Also: a dry run reached an approval nobody could answer (a dry run is not saved, so it cannot wait; pass `--approve`, or drive it with `--control stdio`). |
| `2` | The run finished, but some files failed. The other files' changes were written (in a dry run, nothing was), and the output ends with how many failed. A resumed run counts the files that failed in steps it reused. Also: the workflow called [`fail()`](/community/workflows/reference#failing-a-run-with-a-report) (the run is `failed`, and keeps its output). |
| `3` | The run needs input. It stopped at an unanswered approval (resume with `--approve <QUESTION_ID>`), or a resume needs a decision about a step that may already have run (use `--rerun-step <STEP_ID>` or `--skip-step <STEP_ID>`). |
| other | The workflow called `fail(message, { exitCode })` with that code (1 to 125). A workflow that passes `3` exits like a waiting run: check `workflow status` to tell them apart. |

See [Exit codes](/community/workflows/exit-codes) for how to read them in a script.

#### `workflow resume`

Continue a run that failed, was paused (Ctrl-C) or interrupted, or is waiting for approval. A run that was canceled or rejected is over: resuming it takes `--force`. Steps that already finished are not run again: their recorded results are reused, in the order the steps finished the first time. If you changed the workflow, steps you left alone keep their results wherever they now are in the file; a step you added or changed runs, also when it had finished before.

The run continues with what it was started with: `--managed-git` and `--agent` carry over (a new `--agent` or `--model` wins), and flags you pass add to them. A run that another process is still executing cannot be resumed; wait for it or cancel it. One run at a time changes a repository: while a run executes (started or resumed), another run on the same repository (or the same directory, outside a git repository) fails at once, naming the running run and how to `workflow attach` to it or `workflow cancel` it. A run whose process was killed holds nothing: its lock goes with the process. A run started with `runWorkflow` in Node.js is resumed there, not here.

Each run records the codemod version that ran it (`codemodVersion` in `workflow status --format json`). Function and `forEachFile` steps are matched by a hash of the code the CLI builds from them, which another version may build differently. When you resume a run another version made and some finished steps no longer match, `workflow resume` refuses and names the version and the steps: resume it with that version (`npx codemod@<version> workflow resume --id <ID>`), or pass `--force` to run those steps again.

```bash
npx codemod workflow resume --id <ID> [--approve [<QUESTION_ID>]] [--force] [--rerun-step <STEP_ID>] [--skip-step <STEP_ID>]
```

If the process stopped before saving the outcome of a shell, agent, git, pull request, HTTP, or nested codemod step, the step shows as `started`. Check what it already did before you resume. In a terminal, choose **Rerun** or **Skip**; in CI or with `--no-interactive`, the CLI exits `3` and prints the step's ID and the two flags. `--approve` and `--force` do not make this decision for you.

- `--rerun-step <STEP_ID>` runs the step again. It can repeat changes or send the same request twice.
- `--skip-step <STEP_ID>` does not run the step again or undo what it did. The step returns `null`, so the workflow must be able to continue without its result.

Use the step's numeric position from `workflow status`. Repeat the flags to make a choice for each interrupted step.
Runs interrupted before alpha.11 have no started markers, so check for side effects before resuming one.

<ResponseField name="-i, --id <ID>" type="string" required>
  Run ID, from `workflow list` or the end of a failed run's output.
</ResponseField>

<ResponseField name="--approve [QUESTION_ID]" type="string">
  Without an id: give the approval the run is waiting for, and any later ones. `--trigger-all` is accepted as an alias.

  With an id, give only that approval; the run stops again at the next one. Each approval has an id that stays the same across resumes, `approval:<step>` for an `approval(...)` step (`shell:<step>`, `pull-request:<step>` for the others). A run that waits shows it: in its last lines, as `question` in `workflow status`, and in `run_finished` with `--format jsonl`. Repeat `--approve` to give several.

  ```bash
  npx codemod workflow resume --id <ID> --approve approval:3 --no-interactive
  ```
</ResponseField>

<ResponseField name="--force" type="boolean">
  Continue a run that was canceled or rejected. Steps that finished keep their results; the step that was rejected asks again. Also continues a run another codemod version made whose finished function steps no longer match: those run again.
</ResponseField>

<ResponseField name="--allow-dirty" type="boolean">
  For a run that stopped before it first wrote (for example at the check for uncommitted changes): write even if the target has uncommitted changes. A run that already wrote is not checked again.
</ResponseField>

<ResponseField name="--install-skill" type="boolean">
  **Experimental.** In non-interactive resumes, execute pending `installSkill` steps.

  ```bash
  npx codemod workflow resume --id <ID> --approve --no-interactive --install-skill
  ```
</ResponseField>

The run remembers its workflow file, target and parameters, so `-w` and `-t` are not needed.

**`workflow validate`**

Validate a workflow file.

```bash
npx codemod workflow validate -w <workflow.ts|workflow.yaml|directory>
```

`workflow validate` is capability-aware for codemod packages:

- **Workflow-only** package: validates workflow behavior.
- **Skill-only** package: validates workflow `install-skill` behavior plus authored skill layout (`agents/skill/<skill-name>/...`).
- **Workflow + skill** package: validates both executable workflow and authored skill behavior.

<ResponseField name="-w, --workflow <FILE>" type="string" required>
  Path to workflow file or codemod package directory.
</ResponseField>

For `workflow.ts`, validation builds the workflow: it parses it and checks the `forEachFile` callback rules, reporting errors with file, line and column.

For `workflow.yaml`:

| Check                       | Ensures                                          |
| --------------------------- | ------------------------------------------------ |
| Parsing                     | The YAML matches the workflow spec               |
| Unique IDs                  | Node and template IDs are unique                 |
| Dependency validation       | Every `depends_on` exists and there are no cycles |
| Template references         | All `template:` IDs exist                        |
| Matrix validation           | Every matrix has `values` or `from_state`        |
| Translation                 | The workflow translates to TypeScript that builds |

It also lists features the translation drops (for example `state.schema`), refuses features 2.0 does not support yet (`runtime: docker`), and suggests `workflow upgrade`.

<Info>
  Why validate?

  Validation catches issues before execution, saving time and preventing runtime errors.
</Info>

<Accordion title="Validation vs. Logical Correctness">
  `workflow validate` checks that your workflow is well formed, but it cannot verify:

  - **Logical correctness**: Whether your workflow does what you intend
  - **Runtime behavior**: How your workflow behaves with real data
  - **Dependencies**: Whether external files/scripts exist
  - **State consistency**: Whether state updates are logically sound
</Accordion>

**`workflow upgrade`**

Convert `workflow.yaml` files to `workflow.ts`.

```bash
npx codemod workflow upgrade [PATH] [--keep-yaml] [--dry-run]
```

In a package directory (the current directory by default), every YAML workflow declared in `codemod.yaml` (or a bare `workflow.yaml`) is converted to a `.ts` file next to it, `codemod.yaml` is updated to point at it, and the YAML file is removed. Features the conversion drops are listed as warnings and marked in the generated file with `// codemod upgrade:` comments.

Run it in a directory that holds several packages, such as a monorepo of recipes, and every package below it is upgraded. Directories that start with `.`, `node_modules`, `target` and `dist` are skipped.

```bash
npx codemod workflow upgrade .        # every package under the current directory
```

Transform files and their tests are not changed: `codemod jssg test` keeps working on them as before. To run fixtures through the whole workflow, add a [test file](/community/workflows/testing). The generated `workflow.ts` references the `codemod/workflow` types, so `tsc` checks it in any project that depends on `codemod`. If the nearest `package.json` does not, `upgrade` suggests adding it.

<ResponseField name="--keep-yaml" type="boolean">
  Keep the YAML files.
</ResponseField>

<ResponseField name="--dry-run" type="boolean">
  Print the generated TypeScript instead of writing files.
</ResponseField>


<ResponseField name="--allow-fs, --allow-fetch, --allow-child-process" type="boolean">

Declare network requests as `http()` steps and commands as `shell()` steps; callbacks read the target without a flag. See [Callbacks are pure](/community/workflows/reference#callbacks-are-pure).
</ResponseField>

### `codemod jssg`

### `codemod init`

Initialize a new Codemod package project.

```bash
npx codemod init [PATH] [options]
```

In interactive mode, `codemod init` prompts you to choose between a `jssg codemod`, `multi-step workflow`, or `agent skill codemod`. Without a terminal to ask on, or in CI, it behaves as `--no-interactive`: the values come from flags.

An `ast-grep-js` or `hybrid` package keeps its workflow in `src/workflow.ts`, with its transform there as a [`forEachFile`](/community/workflows/reference#foreachfileselector-callback) callback that parses each file with `parse(file, { language })` and rewrites it. A `hybrid` package also has shell scripts in `src/scripts/`, which the workflow runs as ``shell`${import.meta.dirname}/scripts/setup.sh` ``, and ast-grep rules in `src/rules/`. Its tests are in `tests/workflow.test.ts`, which runs the workflow on each fixture in `tests/fixtures` with `node:test`; the `test` script runs them.

You'll also be prompted to create a GitHub Actions publishing workflow. This generates `.github/workflows/publish.yml`:

- **Single codemod repo**: Triggers on `v*` tags (e.g., `v1.0.0`)
- **Monorepo**: Triggers on `*@v*` tags (e.g., `my-codemod@v1.0.0`) and extracts the codemod name

Both workflows use [trusted publishers](/community/publishing#trusted-publishers) with OIDC for secure, passwordless publishing.

[See the publishing guide](/community/publishing#complete-github-actions-workflow) for detailed workflow examples.

### `codemod publish`

Publish a Codemod package to a registry.

```bash
npx codemod publish [PATH] [--format json]
```

What `.gitignore` files in the package ignore is not published, nested ones included, and neither are `node_modules` and `.git` directories at any depth. A `workflow.ts`, and each callback and shard function it imports from its own file, is bundled with what it imports from npm packages; the modules the CLI provides (`codemod/workflow`, `codemod/ast-grep`, `fs`, ...) stay imports, and so do the workflow's imports of its callbacks, which the modules the build extracts import. YAML files it imports (ast-grep rules) are published as they are, and stay imports. A workflow that names a file by path where a callback or rules go does not build, so it does not publish: see [Imported callbacks](/community/workflows/reference#imported-callbacks).

<ResponseField name="[PATH]" type="string">
  Path to codemod directory (defaults to current directory).
</ResponseField>

<ResponseField name="--format json" type="string">
  Print one JSON object with `success`, `registry`, `tag`, and `package` after a successful
  upload. On failure, read stderr and check the nonzero exit code.
</ResponseField>

<Info>
  Package metadata (name, version, access level, etc.) is read from `codemod.yaml`. See [Package Structure](/community/package-structure#package-metadata-codemod-yaml) for configuration options.
</Info>

### `codemod unpublish`

Remove a package or selected version from the registry.

```bash
npx codemod unpublish <PACKAGE> [options]
```

<ResponseField name="<PACKAGE>" type="string" required>
  Package name (e.g., `@org/my-codemod` or `my-codemod`).
</ResponseField>

<ResponseField name="--version <VERSION>" type="string">
  Specific semver to unpublish. Requires confirmation.
</ResponseField>

<ResponseField name="--force" type="boolean">
  Unpublish **all** versions (irreversible). Confirmation required.
</ResponseField>

<ResponseField name="--registry <REGISTRY>" type="string">
  Target registry URL.
</ResponseField>

<ResponseField name="--dry-run" type="boolean">
  Show what would be removed without actually unpublishing.
</ResponseField>

<ResponseField name="--yes, -y" type="boolean">
  Unpublish without asking for confirmation. Without a terminal to ask on (in CI, or with input piped in), `unpublish` refuses to run unless you pass it.
</ResponseField>

<Tip>
  In a terminal, the CLI asks for confirmation when `--version` or `--force` is used, unless you pass `--yes`.
</Tip>

<Accordion title="Examples">
  ```bash
  # Preview removal of a single version
  npx codemod unpublish my-codemod --version 0.1.0 --dry-run
  
  # Remove a single version (will prompt)
  npx codemod unpublish my-codemod --version 0.1.0
  
  # Remove all versions (will prompt)
  npx codemod unpublish my-codemod --force

  # Remove a single version from a script or CI job (no prompt)
  npx codemod unpublish my-codemod --version 0.1.0 --yes
  
  # Unpublish from a custom registry
  npx codemod unpublish my-codemod --force --registry https://registry.example.com
  ```
</Accordion>
