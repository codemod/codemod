---
title: "Semantic Analysis"
description: "Find symbol definitions and references across your codebase using semantic analysis in JSSG codemods"
---

Semantic analysis enables your codemods to understand symbol relationships in code—finding where variables are defined, tracking all references to a function, or discovering cross-file dependencies. This goes beyond pattern matching to provide IDE-like intelligence for your transformations.

## When to enable it

Pattern matching alone is not enough when **symbol origin** matters. In `workflow.ts`, set `semanticAnalysis` on the `forEachFile` selector whose callback calls `parse(file)` (`"file"` by default; `"workspace"` when you need cross-file resolution). In legacy YAML, set `semantic_analysis` on the `js-ast-grep` step. Check symbol origin before you ship if any of these are true:

| Risk | Example | What to do |
| --- | --- | --- |
| Generic method / property name | `$RECV.update(...)`, `.map(...)`, `.get(...)` | Prove the receiver binds to the intended API (import/type), not every same-named call |
| Rename by identifier text | Replace all `Foo` identifiers | Resolve the binding / references from the real import, not a global name regex |
| Aliased or re-exported symbols | `import { createX as cx }` | Follow the binding; do not match only the original export spelling |
| Cross-file move or rename | Update call sites in other modules | Use `workspace` scope |

To ask where a value comes from or goes, who calls a function, or whether a variable changes, see
[Data Flow and Call Graph](/community/jssg/dataflow) (JavaScript and TypeScript, experimental).

Also prefer [`@jssg/utils` binding helpers](/community/jssg/utils/javascript) (`importBindingOf`, `resolveDefinition`, `renameReferences`) instead of reinventing resolution. If you skip semantic analysis, document why in the package README (for example: pure string API shape with no shared method names).

## Analysis Modes

Semantic analysis operates in two modes, each with different performance and accuracy trade-offs:

### File Scope (Default)

Single-file analysis that processes symbols within the current file only. This mode is fast and requires no additional configuration.

**Best for:**

- Quick analysis of local variables
- Single-file transformations
- Dry runs and exploratory analysis

**Limitations:**

- Cannot resolve cross-file imports
- Cannot find references in other files

### Workspace Scope

Workspace-wide analysis that resolves cross-file imports and finds references across your entire project. This mode requires specifying a workspace root.

**Best for:**

- Renaming symbols across files
- Finding all usages of exported functions
- Dependency analysis and migration codemods

**Requirements:**

- Workspace root path must be specified
- Files must be processed (indexed) before cross-file queries work

## API Reference

### `symbols(lang).definition` and `symbols(lang).references`

Import `symbols` from `"codemod:ast-grep"` (`"codemod/ast-grep"` in `workflow.ts`) and call it with
the language you work on. It returns lookups: read-only maps from a node to its edges. See
[Data Flow and Call Graph](/community/jssg/dataflow) for
lookups in general.

```ts
import { symbols } from "codemod:ast-grep";

const { definition, references } = symbols("typescript");

const [def] = definition.get(node) ?? [];
const refs = references.get(def?.nameNode ?? node) ?? [];
```

<ParamField path="lang" type='"typescript" | "tsx" | "javascript" | "jsx" | "python"'>
  The language of the nodes you will ask about. A lookup throws a `TypeError` when the node's
  language family doesn't match.
</ParamField>

<ParamField path="definition.get(node)" type="DefinitionEdge[] | undefined">
  The declaration of the symbol at `node`, as an array with at most one edge. `undefined` when
  there is no definition.
</ParamField>

<ParamField path="references.get(node)" type="ReferenceEdge[] | undefined">
  Every reference to the symbol at `node`, one edge per reference. The edges are not grouped by
  file.
</ParamField>

```ts
interface DefinitionEdge<M> {
  /** The AST node at the declaration */
  node: SgNode<M>;
  /** The declared name inside `node`, or null for an anonymous declaration */
  nameNode: SgNode<M> | null;
  /** 'local', 'import' or 'external' */
  kind: "local" | "import" | "external";
  /** How the declaration is exported from its module ("default" or the name), or null */
  exportName: string | null;
}

interface ReferenceEdge<M> {
  /** The AST node of one reference */
  node: SgNode<M>;
}
```

<ResponseField name="node" type="SgNode">
  The node the edge lands on. Its file is `node.getRoot()`, an `SgRoot` with `filename()`,
  `relativeFilename()` and `write(text)`.
</ResponseField>

<ResponseField name="nameNode" type="SgNode | null">
  Definition edges only. The declared name, ready to pass to `references.get()`.
</ResponseField>

<ResponseField name="kind" type='"local" | "import" | "external"'>
  Definition edges only. Where the declaration was found.
</ResponseField>

<ResponseField name="exportName" type="string | null">
  Definition edges only. How a codemod must import the declaration.
</ResponseField>

**Ask on a name node.** Pass an identifier, such as a declarator's `field("name")` or a use of the
name. Asking on a whole statement gives no edges.

**Definition always follows imports.** A use of an imported name (`Modal` in `<Modal />`) resolves
through its import binding to the declaration in one call. There is no option to stop at the
import. The edge's `node` can be the name, a whole declarator (`LIMIT: number = 10`) or a whole
`export default function Modal() {}` statement. `nameNode` is always the name, and `exportName`
says how a codemod must import it:

```ts
// import { Modal, formatValue } from "./components" (a barrel)
const [def] = definition.get(use) ?? [];
def.node.getRoot().filename(); // ".../modal.tsx"
def.exportName; // "default": import Modal from "./modal"
def.nameNode?.text(); // "Modal"
// For `function format() {}; export { format as formatValue }`:
// exportName "formatValue", nameNode.text() "format"
```

**Definition kinds:**

- `'local'`: the declaration is in the same file (local variable, function, class, etc.).
- `'import'`: the import couldn't be followed (for example, an installed package). The edge lands
  on the import binding in this file (the import specifier, or the default or namespace name). Asking on the imported name itself
  gives the same edge. In file scope, imports are not followed into other files, so an import of
  another workspace file also gives `kind: 'import'`.
- `'external'`: the declaration is in a different file in the workspace.

**`definition.get()` and `references.get()` return `undefined` when:**

- Semantic analysis is off for the step
- No symbol is found at this node (for example, you asked on a whole statement)

**Scope.** `symbols(lang)` follows the step's scope. In file scope (the default), lookups answer
inside the one file. In workspace scope (`semanticAnalysis: "workspace"`, `semantic_analysis:
workspace` in `workflow.yaml`, or `--semantic-workspace <dir>` for `codemod jssg run`), they find
definitions and references across files.

**Re-exports.** In workspace scope, JS/TS definitions follow re-exports to the original
declaration. An imported name, and the name inside a named re-export (`export { a } from "./a"`,
`export { a as b } from "./a"`, `import { a } from "./a"; export { a }`), resolve to the
declaration, passing through any `export *` on the way. Module specifiers resolve as the root
tsconfig says (its `paths`), and through workspace packages linked in `node_modules`. A bare
specifier that doesn't resolve that way is tried again with the tsconfig nearest the importing
file. To resolve a specifier yourself, use `symbols(lang).resolveModule()` and
`symbols(lang).specifierFor()` (see
[Data Flow and Call Graph](/community/jssg/dataflow)).

In workspace scope, `references.get()` on an exported declaration also finds uses in files that
import it through barrels, plus the source-side name of each named re-export (`a` in
`export { a as b } from "./a"`). An `export *` is followed but has no edge of its own. On a name
inside a re-export, it answers for the declaration being re-exported.

<Note>
  When a symbol comes from an import that can't be followed (for example,
  `import x from "some-external-module"`), `definition.get()` returns one edge with
  `kind: 'import'` that points at the import binding in this file. You can still trace the
  symbol back to where it was imported.
</Note>

**Python.** Use `symbols("python")`. Definitions and references work the same way, with the
same edge shape. In workspace scope they resolve across modules.

**Grouping by file.** References come as one flat list. To group them, key on the file:

```ts
const byFile = new Map(); // filename -> { file, nodes }
for (const edge of refs) {
  const file = edge.node.getRoot();
  const entry = byFile.get(file.filename()) ?? { file, nodes: [] };
  entry.nodes.push(edge.node);
  byFile.set(file.filename(), entry);
}
```

**Listing.** Lookups are answered node by node. `size`, `keys()` and `for...of` throw on a
built-in lookup. Ask `get(node)` instead.

### Migrating from `definition()` and `references()`

The SgNode methods `definition(options?)` and `references()` are removed. Use the lookups from
`symbols(lang)` instead.

- `def.root` is gone. Use `def.node.getRoot()`.
- `{ follow: true }` is now the only behavior. `resolveExternal` is gone.
- `def === null` becomes `!def`.
- References are flat edges, not `{ root, nodes }` groups. Use `edge.node.getRoot()` for the file.

<CodeGroup>
```ts Before
const def = use.definition({ follow: true });
def?.root.write(newText);

for (const file of name.references()) {
  for (const n of file.nodes) {
    edits.push(n.replace("newName"));
  }
}
```

```ts After
import { symbols } from "codemod:ast-grep";

const { definition, references } = symbols("typescript");

const [def] = definition.get(use) ?? [];
def?.node.getRoot().write(newText);

for (const { node: n } of references.get(name) ?? []) {
  edits.push(n.replace("newName"));
}
```
</CodeGroup>

### `root.write(content)`

Write content to another file. Use it on an `SgRoot` from `def.node.getRoot()` or from a reference's
`edge.node.getRoot()`. This method allows cross-file editing within a single codemod execution.

<ParamField path="write(content)" type="void">
  Writes the provided content to the file and updates the semantic provider's
  cache.
</ParamField>

```ts
// Rename a declaration in the file that holds it
const { definition } = symbols("typescript");
const [def] = definition.get(node) ?? [];
const defFile = def?.node.getRoot();
if (def?.nameNode && defFile.filename() !== root.filename()) {
  const edits = [def.nameNode.replace("newName")];
  const newContent = defFile.root().commitEdits(edits);
  defFile.write(newContent);
}
```

**Throws an error when:**

- Called on the current file being processed (use `return` instead)
- The file has no path
- The write operation fails

<Warning>
  You cannot call `write()` on the current file. For the current file, return
  the modified content from `transform()` instead.
</Warning>

## Using Semantic Analysis

### Via Workflow Configuration (Recommended)

The recommended way to use semantic analysis is through workflow files. Create a `workflow.yaml` that references your codemod script:

<CodeGroup>
```yaml workflow.yaml (File Scope)
version: "1"
nodes:
  transform:
    js-ast-grep:
      js_file: scripts/codemod.ts
      semantic_analysis: file
```

```yaml workflow.yaml (Workspace Scope)
version: "1"
nodes:
  transform:
    js-ast-grep:
      js_file: scripts/codemod.ts
      semantic_analysis: workspace
```

```yaml workflow.yaml (Custom Root)
version: "1"
nodes:
  transform:
    js-ast-grep:
      js_file: scripts/codemod.ts
      semantic_analysis:
        mode: workspace
        root: ./path/to/workspace
```

</CodeGroup>

<ParamField path="semantic_analysis" type="string | object">
Configure semantic analysis mode. Can be:
- `"file"` — Single-file analysis (default)
- `"workspace"` — Workspace-wide analysis using the target path
- `{ mode: "workspace", root: "./path" }` — Workspace-wide with custom root

In `workflow.ts`, the `forEachFile` selector's `semanticAnalysis` option takes the same values, and `"none"` turns analysis off.
</ParamField>

**Run the workflow:**

```bash
npx codemod workflow run -w /path/to/codemod/workflow.yaml -t /path/to/target
```

<ParamField path="-w, --workflow" type="PATH">
  Path to the workflow YAML file.
</ParamField>

<ParamField path="-t, --target" type="PATH">
  Path to the target directory containing files to transform.
</ParamField>

<Info>
When a lookup edge points into another file, `edge.node.getRoot().relativeFilename()` gives that file's path relative to the active target directory.
</Info>

### Renaming a Utility Function Across Files (TypeScript)

This example renames `formatDate` to `formatDateTime` across a multi-file TypeScript project.

**Source codebase:**

<CodeGroup>
```typescript src/utils/date.ts

  return date.toISOString().split('T')[0];
}

export function parseDate(str: string): Date {
  return new Date(str);
}
```

```typescript src/components/EventCard.tsx
  title: string;
  date: Date;
}

export function EventCard({ title, date }: Event) {
  return (
    <div className="event-card">
      <h3>{title}</h3>

    </div>
  );
}
```

```typescript src/pages/Dashboard.tsx
import { formatDate } from "../utils/date";

export function Dashboard({ events }) {
  return (
    <div>
      <h1>Upcoming Events</h1>
      {events.map((event) => (
        <p key={event.id}>
          {event.name} - {formatDate(event.scheduledAt)}
        </p>
      ))}
    </div>
  );
}
```

</CodeGroup>

**Codemod and workflow:**

<CodeGroup>
```typescript scripts/rename-format-date.ts
import { symbols } from "codemod:ast-grep";

export default function transform(root) {
  const rootNode = root.root();
  const currentFile = root.filename();
  const { references } = symbols("typescript");

  // Find the function declaration we want to rename
  const funcDeclName = rootNode.find({
    rule: {
      pattern: "formatDate",
      inside: {
        pattern: "export function formatDate($$$PARAMS) { $$$BODY }",
        stopBy: {
          kind: "export_statement",
        },
      },
    },
  });

  if (!funcDeclName) return null;

  // Find all references across the workspace, grouped by file
  const editsByFile = new Map(); // filename -> { file, edits }
  for (const { node } of references.get(funcDeclName) ?? []) {
    const file = node.getRoot();
    const entry = editsByFile.get(file.filename()) ?? { file, edits: [] };
    entry.edits.push(node.replace("formatDateTime"));
    editsByFile.set(file.filename(), entry);
  }

  // Write changes to other files
  for (const [filename, { file, edits }] of editsByFile) {
    if (filename === currentFile) continue;
    file.write(file.root().commitEdits(edits));
  }

  return rootNode.commitEdits(editsByFile.get(currentFile)?.edits ?? []);
}

```

```yaml workflow.yaml
      js_file: scripts/rename-format-date.ts
```


</CodeGroup>

### Finding Usages of a Python Class

Analyze how a class is used across a Python project without making changes.

**Source codebase:**

```python models/user.py
    def __init__(self, name: str, email: str):
        self.name = name
```

```python services/auth.py

        return User(name=username, email=f"{username}@example.com")

```

```python api/routes.py
from models.user import User
from services.auth import authenticate

    user = authenticate(request.username, request.password)
    if not user:
        raise AuthError("Invalid credentials")
    return user
```

</CodeGroup>

**Codemod and workflow:**

<CodeGroup>
```typescript scripts/analyze-user-class.ts
import { symbols } from "codemod:ast-grep";

export default function transform(root) {
  const rootNode = root.root();
  const { references } = symbols("python");

  // Find the User class definition
  const classDefName = rootNode.find({
    rule: { pattern: "User", inside: { pattern: "class User: $$$BODY" } },
  });

  if (!classDefName) return null;

  const refs = references.get(classDefName) ?? [];

  // Group the flat list of edges by file
  const nodesByFile = new Map(); // filename -> nodes
  for (const { node } of refs) {
    const filename = node.getRoot().filename();
    nodesByFile.set(filename, [...(nodesByFile.get(filename) ?? []), node]);
  }

  // Log usage analysis
  console.log("=== User class usage analysis ===\n");

  for (const [filename, nodes] of nodesByFile) {
    console.log(`📄 ${filename}:`);
    for (const node of nodes) {
      const line = node.range().start.line + 1;
      const context = node.parent()?.text().slice(0, 50) || node.text();
      console.log(`   Line ${line}: ${context}...`);
    }
    console.log("");
  }

  console.log(`Total: ${refs.length} usages across ${nodesByFile.size} files`);

  return null; // Analysis only, no changes
}

```

### Tracing External Module Imports

Find where external dependencies are imported when `node_modules` isn't available.

**Source codebase:**

<CodeGroup>
```typescript src/api/client.ts
import axios from 'axios';
import { z } from 'zod';

const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
});

export async function fetchUser(id: string) {
  const response = await axios.get(`/api/users/${id}`);
  return UserSchema.parse(response.data);
}
```

```typescript src/hooks/useUser.ts
import { useQuery } from "@tanstack/react-query";
import { fetchUser } from "../api/client";

export function useUser(userId: string) {
  return useQuery({
    queryKey: ["user", userId],
    queryFn: () => fetchUser(userId),
  });
}
```

</CodeGroup>

**Codemod and workflow:**

<CodeGroup>
```typescript scripts/trace-external-imports.ts
import { symbols } from "codemod:ast-grep";

export default function transform(root) {
  const rootNode = root.root();
  const { definition } = symbols("typescript");

  // Identifiers that might be external imports
  const identifiers = ["axios", "z", "useQuery"];

  for (const name of identifiers) {
    // The first identifier with this name (the one in the import, if any)
    const node = rootNode.find({ rule: { kind: "identifier", regex: `^${name}$` } });
    if (!node) continue;

    const [def] = definition.get(node) ?? [];
    if (!def) continue;

    if (def.kind === "import") {
      // External module: couldn't follow it, so the edge is the import binding
      const statement = def.node.ancestors().find((a) => a.kind() === "import_statement");
      console.log(`${name}: External import`);
      console.log(`  Import statement: ${statement?.text() ?? def.node.text()}`);
    } else if (def.kind === "local") {
      console.log(`${name}: Defined locally at line ${def.node.range().start.line + 1}`);
    } else if (def.kind === "external") {
      console.log(`${name}: Defined in ${def.node.getRoot().filename()}`);
    }
  }

  return null;
}

```

### Cross-File Editing with Definition Lookup

Rename a constant and update all files that import it.

**Source codebase:**

<CodeGroup>
```typescript src/constants.ts
export const API_BASE_URL = "https://api.example.com";
export const API_TIMEOUT = 5000;
export const MAX_RETRIES = 3;
```

```typescript src/api/client.ts
import { API_BASE_URL, API_TIMEOUT } from "../constants";

export const client = {
  baseURL: API_BASE_URL,
  timeout: API_TIMEOUT,
};
```

```typescript src/config/index.ts
import { API_BASE_URL } from "../constants";

export const config = {
  apiUrl: API_BASE_URL,
  debug: process.env.NODE_ENV === "development",
};
```

</CodeGroup>

**Codemod and workflow:**

<CodeGroup>
```typescript scripts/rename-constant.ts
import { symbols } from "codemod:ast-grep";

export default function transform(root) {
  const rootNode = root.root();
  const currentFile = root.filename();
  const { references } = symbols("typescript");

  // Find the constant declaration
  const constDeclName = rootNode.find({
    rule: {
      pattern: "API_BASE_URL",
      inside: {
        pattern: "export const API_BASE_URL = $VALUE",
        stopBy: {
          kind: "export_statement",
        },
      },
    },
  });

  if (!constDeclName) return null;

  // Find all references to API_BASE_URL, grouped by file
  const editsByFile = new Map(); // filename -> { file, edits }
  for (const { node } of references.get(constDeclName) ?? []) {
    const file = node.getRoot();
    const entry = editsByFile.get(file.filename()) ?? { file, edits: [] };
    entry.edits.push(node.replace("API_ENDPOINT"));
    editsByFile.set(file.filename(), entry);
  }

  for (const [filename, { file, edits }] of editsByFile) {
    if (filename === currentFile) continue;
    file.write(file.root().commitEdits(edits));
  }

  return rootNode.commitEdits(editsByFile.get(currentFile)?.edits ?? []);
}

```

<Warning>
  You cannot call `write()` on the current file being processed. For the current
  file, return the modified content from `transform()` instead. This ensures the
  engine properly tracks and applies changes.
</Warning>

<Note>
  When you call `write()` on an `SgRoot` from `def.node.getRoot()` or a reference's
  `edge.node.getRoot()`, the semantic provider's cache is automatically updated. This
  ensures subsequent semantic queries reflect the changes.
</Note>

## Best Practices

<AccordionGroup>
<Accordion title="Use file scope for single-file transformations">
File scope analysis is faster and doesn't require workspace configuration. Use it when your codemod only needs to understand symbols within a single file.

```yaml workflow.yaml
version: "1"
nodes:
  transform:
    js-ast-grep:
      js_file: scripts/codemod.ts
      semantic_analysis: file # Fast, single-file analysis
```

</Accordion>

<Accordion title="Handle undefined/empty results gracefully">
Lookups may return `undefined` or an empty list for various reasons. Always check return values:

```ts
const { definition, references } = symbols("typescript");

const [def] = definition.get(node) ?? [];
if (!def) {
  // No definition: not a name node, unresolved, or semantic analysis is off
  return null;
}

const refs = references.get(def.nameNode ?? node) ?? [];
if (refs.length === 0) {
  // No references found
  return null;
}
```

</Accordion>

<Accordion title="Check file ownership before editing">
When processing references across files, verify you're editing the correct file:

```ts
for (const { node } of refs) {
  // Only edit the current file
  if (node.getRoot().filename() === root.filename()) {
    edits.push(node.replace("newText"));
  }
}
```

</Accordion>
</AccordionGroup>

## Troubleshooting

<AccordionGroup>
<Accordion title="Lookups return undefined/empty">
**Possible causes:**
- The node is not a name. Ask on an identifier (for example a declarator's `field("name")`), not on a whole statement
- Semantic analysis is turned off for the step (`semanticAnalysis: "none"`), or the symbol is in another file and the step uses the default file scope (use `semanticAnalysis: "workspace"`, or `semantic_analysis: workspace` in `workflow.yaml`)
- The language isn't supported (only JavaScript/TypeScript and Python)
- The symbol couldn't be resolved (external library, syntax error)

**Debug steps:**

```ts
const { definition } = symbols("typescript");
const [def] = definition.get(node) ?? [];
console.log("Definition:", def);
console.log("Node text:", node.text());
console.log("Node kind:", node.kind()); // expect "identifier" or another name kind
```

If a lookup throws a `TypeError`, the node's language family doesn't match the language you passed
to `symbols()`.

</Accordion>

<Accordion title="Cross-file references not found">
**Possible causes:**
- Using file scope mode instead of workspace scope
- The target file hasn't been indexed yet
- Import resolution failed

**Solution:**
Ensure you're using workspace scope mode in your workflow:

```yaml workflow.yaml
version: "1"
nodes:
  transform:
    js-ast-grep:
      js_file: scripts/codemod.ts
      semantic_analysis: workspace
```

Then run:

```bash
npx codemod workflow run -w /path/to/codemod/workflow.yaml -t /path/to/target
```

</Accordion>

<Accordion title="Performance issues with large workspaces">
**Tips:**
- Start with file scope for initial development
- Use workspace scope only when cross-file analysis is needed
- Consider running workflows on subsets of your codebase by targeting specific directories
</Accordion>
</AccordionGroup>
