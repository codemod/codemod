---

<Warning>
  Experimental. The API can change between releases. JavaScript and TypeScript only (JSX and TSX
  syntax included; types are not used).
</Warning>

[`definition()` and `references()`](/community/jssg/semantic-analysis) answer questions about
names. These methods answer questions about **values and calls**, so a codemod can decide whether
a rewrite is safe before it makes it:

| Question | Call |
| --- | --- |
| What is this value computed from? | `node.flowsFrom()` |
| Where does this value go? | `node.flowsTo()` |
| What does this function call? | `node.callees()` |
| Who calls this function? | `node.callers()` |
| Is this variable, or the object it holds, changed? | `node.mutations()` |

Each answer is an array of objects that carry `node` and `root`, so you can go straight from an
answer to an edit. On top of them: `dependsOn()` / `reaches()` booleans, `key()` / `equals()` to
compare nodes across answers, and module resolution on the root (`resolveModule()`,
`resolveExport()`, `specifierFor()`) for codemods that rewrite imports.

## Turn it on

The methods use the step's semantic analysis. Set `semanticAnalysis: "file"` (the default) for
`flowsFrom`, `flowsTo` and `mutations`, which stay inside one file, and `"workspace"` for the call
graph across files and for module resolution:

```ts workflow.ts
import { step, forEachFile } from "codemod/workflow";
import { parse } from "codemod/ast-grep";
import transform from "./scripts/sql.ts";

export default async function main() {
  await step(
    "Parameterize queries",
    forEachFile(
      { include: "src/**/*.ts", language: "typescript", semanticAnalysis: "workspace" },
      (file) => {
        const out = transform(parse(file));
        if (typeof out === "string") file.write(out);
      },
    ),
  );
}
```

Roots that the callback parses with `parse(file)` get the selector's analysis. In `workflow.yaml`,
use `semantic_analysis: workspace` on the `js-ast-grep` step; with `codemod jssg run`, pass
`--semantic-workspace <dir>`.

<Note>
  The queries **throw** instead of answering `[]` when they cannot run: semantic analysis is off,
  the file is not JavaScript or TypeScript, the root was parsed from a string, or the codemod runs
  on the Node.js host (`codemod/host`, `codemod/testing`'s default) or in WebAssembly. An empty
  answer would read as "no callers" or "no sources", and a codemod might act on it. Unknown options
  throw too, so a typo cannot silently change an answer. On the Node.js host, test with
  `{ host: "quickjs" }`.

  A query on a node it does not apply to throws a `TypeError` that names the node's kind and what
  to ask instead: `flowsFrom()` / `flowsTo()` on a statement or declaration, `mutations()` on
  anything but a variable or a use of one (for `a.b`, ask about `a`), `callers()` on code outside
  any function. A part of a value (the `limit` in `req.query.limit`) answers for that value. An
  expression the analysis does not track, such as `typeof import("./x")` in a type position, answers
  `[]`, so a loop over pattern matches does not stop on one.
</Note>

## Where does a value come from: `flowsFrom()`

```ts
// db.query("select ... " + id) where the text depends on the request:
// rewrite to a parameterized query.
for (const call of root.root().findAll({ rule: { pattern: "$DB.query($SQL)" } })) {
  const sql = call.getMatch("SQL")!;
  if (!sql.dependsOn((step) => step.kind === "parameter" && step.name === "req")) continue;
  // ...
}
```

Steps come nearest first. Each has:

| Field | Meaning |
| --- | --- |
| `node`, `root` | The syntax node of the step, and its root |
| `kind` | `variable`, `parameter`, `import`, `reference`, `call`, `member`, `literal`, `global`, `this`, `function`, `class`, `object`, `array`, `jsx`, `jsx-attribute`, `expression` |
| `via` | The edge that reached it: `assign`, `read`, `alias`, `property`, `element`, `argument`, `receiver`, `derive`, `capture`, `store`, `jsx-attribute`, `jsx-child`, `return` |
| `name` | Always set for parameters, variables, imports, references, globals and calls (a call's name is the callee text, `"db.query"`); `null` when there is none |
| `index` | The parameter's position; for `via: "argument"`, the argument's position |
| `depth` | Edges from the queried node; `1` is a direct source |
| `from` | The step this one was reached from (`null` at depth 1). Walk it to print a path |
| `boundary` | The trail ends here because the value comes from outside the analyzed code: a parameter, an import, a global, `this`, or a call result |

Options: `throughCalls` (default `true`: a call's result counts as derived from its arguments and
receiver, and the walk continues into them), `maxDepth`, `stopAt` (edge kinds to report but not
walk past), and `interprocedural` (default `false`: cross function boundaries inside the workspace;
a parameter continues at its callers' arguments, a call's result at the callee's returns, and the
answer can span files, so `step.root` and `step.from` may be in another file).

```ts
// The value a variable was initialized with: the step after the variable.
const init = sql.flowsFrom().find((s) => s.via === "assign" && s.from?.kind === "variable");
```

## Where does a value go: `flowsTo()`

The same steps, forward. A step with `via: "argument"` is a call that receives the value; a
`return` or `store` (`o.p = x`) step is reported and not followed further.

```ts
// Every call that receives a value derived from req.body
const calls = root.root().findAll({ rule: { pattern: "req.body" } })
  .flatMap((body) => body.flowsTo())
  .filter((step) => step.via === "argument")
  .map((step) => step.node);

// Where is this string first used? Stop at the first JSX sink.
const sinks = literal.flowsTo({ stopAt: ["jsx-attribute", "jsx-child", "return"] });
```

`node.reaches(target)` is `true` when a step is `target` (a node) or matches a predicate:
`body.reaches((s) => s.via === "argument" && s.name === "db.query")`.

## Who calls this: `callers()`

One entry per call. `node` is the calling function (or the call, for module top-level code,
`name: "<module>"`), `callSite.node` is the call to edit, and `callee` is the function that call
reaches. Needs workspace scope to see other files.

```ts
// loadConfig() becomes async: await every call and make every caller async, across files.
// A function handed to unknown code (names.map(getSetting)) gets a TODO and is not followed.
const callers = loadConfig.callers({ transitive: true, stopAt: ["callback"] });
if (callers.truncated || callers.unparsed.length > 0) {
  throw new Error("call graph incomplete: not propagating async");
}
const seen = new Set<string>();
for (const caller of callers) {
  if (seen.has(caller.callSite.node.key())) continue;
  seen.add(caller.callSite.node.key());
  if (caller.via === "callback") {
    // TODO: `${caller.callee?.name}` is async now
    continue;
  }
  // await caller.callSite.node; make caller.node async (once per function: key())
}
```

<Warning>
  **No callers does not mean unused.** Getters and setters run on property reads and writes
  (`obj.value`), which are not calls, so they have no callers either. A function stored as a value (`{ round: fn }`,
  `export default fn`) or called dynamically has no callers the graph can see. Before deleting,
  also check that `references()` finds nothing but the declaration, and that the answer is
  complete (`!truncated && unparsed.length === 0`).
</Warning>

## What does this call: `callees()`

The answer depends on the node you ask:

| Node | `callees()` answers |
| --- | --- |
| The program, `root.root()` | Calls made while the module is evaluated (top-level code) |
| A call or a JSX element | What that call calls: for `<Modal />`, the `Modal` component |
| A function or its name | The calls written in its body |
| Any other code (a statement, a block) | The calls written inside it |

Each entry is a resolved function (`resolved: true`, `node` is the
function, possibly in another file, `callSite` is the call) or a call the analysis could not
resolve (`resolved: false`, `name` is the callee text: `"Number"`, `"res.json"`).

```ts
const component = element.callees().find((c) => c.resolved && c.via === "jsx");
const sideEffects = root.root().callees(); // does importing this module run code?
```

`via` says why the edge exists: `direct`, `method`, `constructor`, `jsx`, `callback` (the
function is passed to code the analysis cannot see, `items.map(f)`, and is assumed to be called),
or `type` (resolved by the receiver's type, see [Types](#types-the-typescript-7-checker)).

## Types: the TypeScript 7 checker

Values alone can't resolve `repo.save()` when `repo` is a parameter, a context object or a call
result. With types on, the TypeScript 7 checker answers instead (experimental):

- `callees()` and `callers()` follow `x.m()` by the type of `x`, marked `via: "type"`. For an
  interface or property-signature member, the edge goes to every class member or object property
  that implements it (up to 16; past that the call stays unresolved).
- An unresolved call gets a `declaration` (`{ node, root, name }`) when the checker knows where the
  member is declared but it is not workspace code: `list.push()` in `lib.es5.d.ts`, a Solid
  `isOpen: Accessor<boolean>`.
- `node.typeInfo()` returns the type as the checker prints it: `"UserRepo"`,
  `"{ id: string; }"`. It is `null` with types off.

Turn them on for a step:

```ts
forEachFile(
  {
    include: "src/**/*.{ts,tsx}",
    semanticAnalysis: { mode: "workspace", types: "ts7" },
  },
  (file) => { /* ... */ },
);
```

In `workflow.yaml`: `semantic_analysis: { mode: workspace, types: ts7 }`.

What types need:

| Need | Why |
| --- | --- |
| `typescript@7.0.x` in the target's `node_modules`, or `CODEMOD_TS_API` set to its `tsc` binary (`node_modules/@typescript/typescript-<os>-<arch>/lib/tsc`) | The checker. Other versions are not used: its protocol changes between minors. `CODEMOD_TS_API=off` turns types off everywhere |
| The target's dependencies installed (`node_modules` present), from a full install that runs before this step | Without them, everything from a library is `any` and calls on it stay unresolved. Measured: 7.6% of all calls resolved through types in a repository with dependencies installed, 1.2% across repositories without |
| A tsconfig (or jsconfig with `allowJs`) | The checker uses the nearest one; files outside any get default options. JSDoc types work in `.js` files |

Types are a snapshot: the checker reads the files once, so edits made during the run are not
reflected (the same rule as `callers()`). They cost a side process (about 200–350 MB of memory)
and a few seconds on a large workspace, the first time a query needs them.

## Is it changed: `mutations()`

Places that change the variable at the node, or the object it holds: reassignments, `++`, property
writes, `delete`, method calls, and calls it is passed to. Changes through another variable holding
the same value come back with `viaAlias: true`; changes inside a nested function with
`deferred: true`. `confidence` is `definite` (a write in the syntax), `likely` (a method known to
mutate, like `push`) or `maybe` (a call with no summary).

```ts
// moment's d.add(...) mutates d. With the result unused, rewrite to d = d.add(...);
// flag changes through aliases or callbacks for review.
for (const m of due.mutations()) {
  if (m.kind !== "method-call" || !MUTATORS.includes(m.name!)) continue;
  if (m.viaAlias || m.deferred) {
    // TODO comment: cannot rewrite in place
  }
}
// Is `items` changed after audit()? `after` takes a node of the same file.
const changed = items.mutations({ after: auditCall }).some((m) => m.confidence !== "maybe");
```

## Compare nodes: `key()` and `equals()`

Each query wraps nodes in new objects, and other files in new roots, so `===` and `id()` do not
match across answers. `node.key()` is a string (file, range, kind) that does; `a.equals(b)` compares
keys. Use keys in a `Set` to edit each function once.

## Rewrite imports: module resolution

On the root, in workspace scope:

| Call | Answer |
| --- | --- |
| `root.resolveModule("@/ui")` | The file an import in this file resolves to (tsconfig `paths` with `extends`, workspace packages, index files), or `null` |
| `root.resolveExport("@/ui", "Modal")` | What the export lands on through barrels and `export *`: a `definition()` result with `exportName` (`"default"` or the name) and `nameNode` |
| `root.specifierFor(modal.root, { like: "@/ui" })` | A specifier that reaches the file, in the style of `like` (relative or alias, `.js` or not), checked by resolving it: `"@/ui/modal"` |
| `root.importers(target?)` | Every place that refers to a module (this file by default): `import` (side-effect imports too, and `import` lines in `.mdx` / `.md`), `export … from`, `require()`, `import()` and test mocks (`jest.mock`, `vi.importActual`, ...), with `kind`, `specifier` and `unparsed`. A snapshot taken on the first query, like `callers()` |
| `root.publicSpecifiers()` | The specifiers other packages import this file with: its package name when it is the entry (`main`, or `exports["."]`), and `exports` subpaths. Empty for private files |
| `root.hasTopLevelEffects()` | Whether importing the module runs code: a top-level call, an `import "./x"` side-effect import, or a top-level write to an object member |

`specifierFor` keeps to a workspace package's public API: for a file in another package it only
offers that package's name and its `exports` subpaths (without `exports`, only the name), never a
relative path or alias into its files. When none reaches the file, it answers `null`, and a
debarrel rewrite keeps the original import.

```ts
// Delete a barrel only when nothing imports it any more and skipping it skips no side effects.
const left = barrel.importers();
const deletable = left.length === 0 && left.unparsed.length === 0 && !barrel.hasTopLevelEffects();
```

`definition({ follow: true })` goes from a use of an imported name to its declaration in one call.
`@jssg/utils` builds a debarrel rewrite on these:
[`importFromDeclarations`](/community/jssg/utils/javascript#importfromdeclarations).

## Cookbook

Short recipes taken from codemods built on these queries. Each one rewrites only when the answer
is complete, and flags the rest.

### Is this SQL built from request data?

```ts
// db.query("select ... " + id) -> db.query("select ... ?", [id])
for (const call of root.root().findAll({ rule: { pattern: "$DB.query($SQL)" } })) {
  const sql = call.getMatch("SQL")!;
  if (!sql.dependsOn((s) => s.kind === "parameter" && s.name === "req")) continue;
  // The text is built in the argument, or in the variable passed: its initializer.
  const init = sql.flowsFrom().find((s) => s.via === "assign" && s.from?.kind === "variable");
  const built = sql.is("identifier") ? init?.node : sql;
  // ...split `built` into text and parameters, then edit `built` and the call's arguments
}
```

### Delete exported functions nobody uses

```ts
for (const fn of root.root().findAll({ rule: { kind: "function_declaration", inside: { kind: "export_statement" } } })) {
  const callers = fn.callers();
  if (callers.length > 0 || callers.truncated || callers.unparsed.length > 0) continue;
  const name = fn.field("name")!;
  // No callers is not enough: a function stored as a value is referenced, not called,
  // and a getter or setter runs on property reads and writes, which are not calls.
  if (name.references().flatMap((f) => f.nodes).some((n) => !n.equals(name))) continue;
  // ...remove the export statement
}
```

### Make a function async, and every caller

```ts
const callers = loadConfig.callers({ transitive: true, stopAt: ["callback"] });
if (callers.truncated || callers.unparsed.length > 0) throw new Error("incomplete call graph");
const seen = new Set<string>();
for (const caller of callers) {
  const call = caller.callSite.node;
  if (seen.has(call.key())) continue;
  seen.add(call.key());
  if (caller.via === "callback") {
    // names.map(getSetting): add a TODO about caller.callee?.name instead
    continue;
  }
  // edit: `await ${call.text()}` in caller.callSite.root; make caller.node async once (key())
}
```

### Import from declarations instead of a barrel

```ts
import { importFromDeclarations } from "@jssg/utils/javascript/modules";

const statements = root.root().findAll({
  rule: { any: [{ kind: "import_statement" }, { kind: "export_statement", has: { field: "source", kind: "string" } }] },
});
const edits = statements.map((s) => importFromDeclarations(root, s)).filter(Boolean);
// import { Button, Modal } from "@/ui"  ->  import { Button } from "@/ui/button"; import Modal from "@/ui/modal"
```

Then, on the barrel itself, decide whether it can go: it has no code of its own, no
`root.hasTopLevelEffects()`, no `root.publicSpecifiers()`, and every entry of `root.importers()`
can be pointed at the declarations (no namespace import, no `require`, no dynamic import whose
members are unknown). Run a type check after the codemod and restore any barrel named in a new error.

### Follow the barrel in test mocks

```ts
import { declarationTargets, retargetImport, retargetMock } from "@jssg/utils/javascript/modules";

const targets = declarationTargets(root, statement);
const edit = retargetImport(statement, (b) => targets.get(b.local) ?? null);
const modules = [...new Set([...targets.values()].map((t) => t.from))];
for (const mock of root.importers(root.resolveModule(source)!)) {
  if (mock.kind !== "mock" || !mock.root.root().equals(root.root())) continue;
  const mockEdit = retargetMock(mock.node, modules); // adds jest.mock("./components/Button"), or repoints a factory
}
```


### Type-check gate

A codemod that removes or moves files (a barrel set aside as `index.barrel.bak.ts`) should prove
the project still type-checks, and undo the changes that broke it. The checker runs in workflow
`shell` steps; [`@jssg/utils/javascript/typecheck`](/community/jssg/utils/javascript#type-check-gate)
maps its errors back to the changes:

```ts workflow.ts
import { step, forEachFile, shell, fail } from "codemod/workflow";
import { parseTypeErrors, newTypeErrors, typeErrorCauses } from "@jssg/utils/javascript/typecheck";
import debarrel from "./scripts/debarrel.ts"; // a forEachFile callback: rewrites imports, file.rename()s barrels

export default async function main() {
  const tsc = () => shell("npx tsc --noEmit -p . --pretty false", { allowFailure: true });
  const before = parseTypeErrors((await step("Type check (before)", tsc())).stdout);

  await step(
    "Debarrel",
    forEachFile({ include: "src/**/*.{ts,tsx}", language: "tsx", semanticAnalysis: "workspace" }, debarrel),
  );

  // The barrels the codemod set aside.
  const { stdout } = await step("Removed barrels", shell("git ls-files --others --exclude-standard -- '*.barrel.bak.*'"));
  const removed = stdout.split("\n").filter(Boolean)
    .map((bak) => ({ from: bak.replace(".barrel.bak", ""), to: null, bak }));

  const after = parseTypeErrors((await step("Type check (after)", tsc())).stdout);
  const causes = typeErrorCauses(newTypeErrors(before, after), removed);

  // Put back each barrel a new error points at, then check once more.
  const restore = removed.filter((change) => causes.has(change));
  if (restore.length > 0) {
    for (const change of restore) await step(`Restore ${change.from}`, shell`mv ${change.bak} ${change.from}`);
    const again = newTypeErrors(before, parseTypeErrors((await step("Type check (again)", tsc())).stdout));
    if (again.length > 0) fail(`${again.length} new type errors after restoring ${restore.length} barrels`);
  }
  if (causes.has(null)) fail(`${causes.get(null)!.length} new type errors not caused by a removed barrel: review the edits`);
}
```

A restored barrel's consumers stay rewritten: the barrel comes back for whatever still needed it
(an import the codemod could not see, such as a non-TypeScript consumer or a generated file). The
step names say which barrels were restored.

## Soundness: what "may" means

The analysis is **not sound**: JavaScript makes that unaffordable. It over-approximates inside what
it models and says where it stops. Build automatic rewrites only on complete answers; flag the rest.

| What it gives up | How you see it |
| --- | --- |
| Values from outside the module: parameters, imports, globals, `this` | `boundary: true` on the step |
| Calls it cannot resolve (libraries, builtins, dynamic calls) | `resolved: false` in `callees()`. Flow treats the result as derived from the arguments (`throughCalls`), so taint is not lost |
| Order of execution | Flow-insensitive: both values of a `let` assigned twice are sources. `mutations({ after })` uses text order plus "same loop" |
| Heap: `o.p = x`, then `o.p` read elsewhere | `flowsTo` reports the write (`via: "store"`) and stops |
| Closures: a callback that reads `x` | Not a flow edge. A mutation inside a nested function is `deferred` and always counts as "after" |
| Control dependence: `c ? a : b` | `a` and `b` are sources, `c` is not |
| Whether an unknown method mutates | `confidence: "maybe"` |
| Callbacks handed to unknown code | Assumed called: `via: "callback"`. Can be a false edge |
| Namespace members (`ns.fn` stored or passed as a value) | `references()` finds `ns.fn` uses through `import * as ns`; check it alongside `callers()` before deleting |
| Files that do not parse | Listed in `unparsed` on call-graph answers; asking about one throws |
| Result limits (50,000 steps or entries) | `truncated: true` on the array |
| Edits during a run | `flowsFrom`, `flowsTo`, `mutations` use current content. `callers()` and `importers()` answer from tables built on their first query: snapshots. A file rewritten later still counts as calling or importing what it did then. Types are a snapshot too |
| Types (with `types: "ts7"`) | `via: "type"` edges trust the declared type: a value cast with `as` or typed `any` is followed as declared, or not at all |

### When the answer is "can't tell"

- **Rewrite** when the answer is complete and has no boundary or `maybe` on the path that matters.
- **Flag** (a TODO comment, a report entry, an agent step) when a `boundary`, `resolved: false`,
  `maybe`, `callback`, `truncated` or `unparsed` touches the decision.
- **Never delete on an empty answer alone.** Check completeness and `references()`.

## Performance

- `flowsFrom`, `flowsTo` and `mutations` touch one file: facts are built the first time a query
  touches it and cached by content.
- `callees({ transitive: true })` builds facts only for the files it reaches.
- The first `callers()` query (and `references()` in workspace scope) walks the whole workspace
  once, in parallel, and keeps a table for the rest of the run. Measured on a 2,500-file, 13 MB
  workspace: about a second for that first query, then well under a millisecond per query. At
  24,000 files (132 MB of source) the first query takes about 13 seconds and the run peaks at about
  3.5 GB of memory: in very large repositories, prefer file-local queries or narrow the target.
- Prefer `maxDepth` and `stopAt` to filtering a long answer.
