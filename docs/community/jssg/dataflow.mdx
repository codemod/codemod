<Warning>
  Experimental. The API can change between releases. JavaScript and TypeScript (JSX and TSX
  syntax included; types only when you turn on the [TypeScript 7 checker](#types-the-typescript-7-checker)),
  and Python with less precision (see [Python](#python)).
</Warning>

These analyses answer questions about **values and calls**, so a codemod can decide whether a
rewrite is safe before it makes it. Most are **lookups**, imported from `codemod/ast-grep`: a
read-only map from a node to the edges that leave it.

| Question | Ask |
| --- | --- |
| What is this value computed from? | `dataflow(lang).sources`, one hop; [`crawl()`](#follow-edges-crawl) follows it |
| Where does this value go? | `dataflow(lang).uses`, one hop; [`crawl()`](#follow-edges-crawl) follows it |
| What does this function call? | `callGraph(lang).callees` |
| Who calls this function? | `callGraph(lang).callers` |
| Is it called from outside the workspace? | `entryPoints(lang)` |
| What type is this expression? | `types(lang).typeOf` |
| Where is this name declared, and used? | `symbols(lang).definition`, `symbols(lang).references` |
| Is this variable, or the object it holds, changed? | `node.mutations()` |
| What can this reach, through calls and framework edges? | [`crawl()`](#follow-edges-crawl) over lookups, with [`join()`](#edges-between-two-patterns-join) for framework edges |

Every edge carries `node`, so you can go straight from an answer to an edit. On top of them:
`key()` / `equals()` to compare nodes across answers, and module resolution
(`symbols(lang).resolveModule()`, `symbols(lang).specifierFor()`, `root.resolveExport()`) for
codemods that rewrite imports.

## Turn it on

Importing `callGraph`, `types`, `entryPoints` or `join` turns workspace analysis on for the code
that imports it, in `forEachFile` callbacks and in plain `step(() => ...)` functions:

```ts workflow.ts
import { step, forEachFile } from "codemod/workflow";
import { callGraph, parse } from "codemod/ast-grep";

export default async function main() {
  const { callers } = callGraph("typescript");
  await step(
    "Await loadConfig",
    forEachFile({ include: "src/**/*.ts", language: "typescript" }, (file) => {
      const fn = parse(file).root().find("function loadConfig() { $$$ }");
      for (const caller of (fn && callers.get(fn)) ?? []) {
        // caller.site is the call, caller.node the function that makes it
      }
    }),
  );
}
```

`dataflow(lang)`, `symbols(lang)` and `node.mutations()` follow the step's scope: one file with the
default `semanticAnalysis: "file"`, the whole workspace with `semanticAnalysis: "workspace"` (so
`symbols(lang).references` finds uses in other files only then). Roots that the callback parses
with `parse(file)` get the step's analysis. In `workflow.yaml`, use `semantic_analysis: workspace` on the `js-ast-grep` step; with
`codemod jssg run`, pass `--semantic-workspace <dir>`.

<Note>
  The queries **throw** instead of answering "nothing" when they cannot run: semantic analysis is
  off, the file is not one the analysis covers, the root was parsed from a string, or the codemod
  runs on the Node.js host (`codemod/host`, `codemod/testing`'s default) or in WebAssembly. An empty
  answer would read as "no callers" or "no sources", and a codemod might act on it. Unknown options
  throw too, so a typo cannot silently change an answer. On the Node.js host, test with
  `{ host: "quickjs" }`.

  A query on a node it does not apply to throws a `TypeError` that names the node's kind and what
  to ask instead: `dataflow(lang)` on a statement or declaration, `mutations()` on
  anything but a variable or a use of one (for `a.b`, ask about `a`), `callers` on code outside any
  function. A part of a value (the `limit` in `req.query.limit`) answers for that value. An
  expression the analysis does not track, such as `typeof import("./x")` in a type position, answers
  nothing, so a loop over pattern matches does not stop on one.
</Note>

### Answers describe the workspace when the step started

Every answer, from `sources` to `callers` and `typeOf`, describes the files as they were when
the step started. A step sees the edits of the steps before it, the same in a real run and in a dry
run, and never its own: a callback that writes a file does not change what the next callback in the
same step is told about it. To ask about an edit, ask in the next step.

A root parsed from text the step produced (`parse({ path, text: edited })` after an edit) does not
match what the answers describe, so a query on it throws `… changed in this step`, instead of
pointing at the wrong code.

## Where does a value come from: `dataflow(lang).sources`

`sources.get(node)` is one hop back: the values this one is computed from. `crawl()` follows the
hops to where they start:

```ts
import { crawl, dataflow } from "codemod/ast-grep";

const { sources } = dataflow("typescript");
// db.query("select ... " + id) where the text depends on the request:
// rewrite to a parameterized query.
for (const call of root.root().findAll({ rule: { pattern: "$DB.query($SQL)" } })) {
  const sql = call.getMatch("SQL")!;
  const origins = await crawl(sources, sql);
  if (![...origins.values()].some((e) => e?.kind === "parameter" && e.name === "req")) continue;
  // ...
}
```

Each edge has:

| Field | Meaning |
| --- | --- |
| `node` | The syntax node the edge reaches |
| `kind` | `variable`, `parameter`, `import`, `reference`, `call`, `member`, `literal`, `global`, `this`, `function`, `class`, `object`, `array`, `jsx`, `jsx-attribute`, `expression` |
| `via` | Why the edge exists: `assign`, `read`, `alias`, `property`, `element`, `argument`, `receiver`, `derive`, `capture`, `store`, `jsx-attribute`, `jsx-child`, `return` |
| `name` | Always set for parameters, variables, imports, references, globals and calls (a call's name is the callee text, `"db.query"`); `null` when there is none |
| `index` | The parameter's position; for `via: "argument"`, the argument's position |
| `boundary` | The value comes from outside the analyzed code here: a parameter, an import, a global, `this`, or a call result |

A call's result counts as derived from its arguments and receiver, so a crawl goes on into them.
The hops stay inside one function: a parameter is where they stop (`boundary: true`); to go on at
the callers' arguments, crawl `callGraph(lang).callers` from the function as well.

In a crawl's result, each edge also has `from`, the node it was reached from, so the path back is
a walk over `from`:

```ts
// The value a variable was initialized with: an `assign` edge from the variable.
const init = [...origins].find(([, e]) => e?.via === "assign" && origins.get(e.from)?.kind === "variable")?.[0];
```

## Where does a value go: `dataflow(lang).uses`

`uses.get(node)` is one hop forward, with the same `kind`, `via`, `name`, `index` and `boundary`
fields. An edge with `via: "argument"` is a call that receives the value; a `return` or `store`
(`o.p = x`) edge is where the value leaves the function or goes into the heap. `crawl()` follows
the hops:

```ts
import { crawl, dataflow } from "codemod/ast-grep";

const { uses } = dataflow("typescript");
// Every call that receives a value derived from req.body
const calls = [];
for (const body of root.root().findAll({ rule: { pattern: "req.body" } })) {
  for (const edge of (await crawl(uses, body)).values()) {
    if (edge?.via === "argument") calls.push(edge.node);
  }
}

// Where is this string used first? One hop: a JSX attribute or child.
const sinks = (uses.get(literal) ?? []).filter((e) => e.via === "jsx-attribute" || e.via === "jsx-child");
```

A crawl goes on past `return` and `store` edges. A `return` edge's node is the function that
returns the value, so from there the crawl follows where the function itself goes, which is not the
value. To stop there, crawl once, then crawl again with the nodes the first crawl reached through
`return` or `store` edges as `stopAt`.

Does the value reach a node? Crawl and ask the result: `(await crawl(uses, body)).has(target)`.

## Who calls this: `callGraph(lang).callers`

One edge per call. `node` is the calling function (or the call, for module top-level code), `site`
is the call to edit, and `via` says why the edge exists. Callers in other files need workspace
analysis, which importing `callGraph` turns on.

```ts
// loadConfig() becomes async: await every call and make every caller async, across files.
// A function handed to unknown code (names.map(getSetting)) gets a TODO and is not followed.
const { callers } = callGraph("typescript");
const reached = await crawl(callers, loadConfig);
for (const [fn, edge] of reached) {
  if (!edge) continue; // loadConfig itself
  if (edge.via === "callback") {
    // TODO: the function passed at edge.site is async now
    continue;
  }
  // await edge.site; make fn async (crawl reaches each function once)
}
```

<Warning>
  **No callers does not mean unused.** `callers` holds call sites in the workspace, nothing else.
  A function its package exports, or a route handler, is called from outside: see
  [`entryPoints(lang)`](#called-from-outside-entrypoints). Getters and setters run on property
  reads and writes (`obj.value`), which are not calls, so they have no callers either. A function
  stored as a value (`{ round: fn }`, `export default fn`) or called dynamically has no callers the
  graph can see. Before deleting, also check that `symbols(lang).references` finds nothing but
  the declaration.
</Warning>

## Called from outside: `entryPoints(lang)`

`entryPoints("typescript")` maps every function in the workspace that something outside its code
calls to why: its package exports it, or a rule you declare matches it.

```ts
const outside = entryPoints("typescript");
outside.get(button);
// [{ kind: "export", label: "@acme/ui#Button" }]
for (const [fn, reasons] of outside) {
  // reasons: [{ kind: "http", label: "GET app/api/users/[id]/route.ts" }], ...
}
```

`kind` is `"export"` for a package export, else the declaring rule's `kind`. Unlike the other
lookups, it lists its entries (`size`, `keys()`, `for...of`), and it is not something to crawl
through: pass it as `crawl()`'s start to walk from every entry point.

A package export counts when the function is exported, directly or re-exported, from a module
the package's `exports` points at (without `exports`: `main`, `module`, `types` or `source`).

Route handlers, tasks and other functions a framework calls are entry points only when you
declare them, on the selector:

```ts
forEachFile(
  {
    include: "app/**/*.ts",
    semanticAnalysis: {
      mode: "workspace",
      entryPoints: [
        { files: "app/**/route.ts", exports: ["GET", "POST", "PUT", "PATCH", "DELETE"], kind: "http" },
        { decorators: ["*.route", "shared_task"], kind: "handler" },
      ],
    },
  },
  (file) => { /* ... */ },
);
```

| Rule field | Matches |
| --- | --- |
| `files` | A glob over the path from the workspace root. `**` crosses directories; brackets are literal, so `[id]` matches a Next.js segment |
| `exports` | Functions exported from a matching file under one of these names (`"default"` for the default export) |
| `decorators` | Functions with a decorator of this name, without its arguments (`app.route` for `@app.route("/x")`); `*` matches any run of characters. Python only for now |
| `kind` | A name for what the rule matches, so you can tell routes from tasks |

A rule names `exports`, `decorators` or both (then a function must match both). `entryPoints` rules
are only accepted with `semanticAnalysis: "workspace"`.

A function that has callers can still be dead: when no caller is an entry point or reached from
one, nothing runs it. To check, [crawl](#follow-edges-crawl) from `entryPoints("typescript")`.

## What does this call: `callGraph(lang).callees`

The answer depends on the node you ask:

| Node | `callees.get(node)` answers |
| --- | --- |
| The program, `root.root()` | Calls made while the module is evaluated (top-level code) |
| A call or a JSX element | What that call calls: for `<Modal />`, the `Modal` component |
| A function or its name | The calls written in its body |
| Any other code (a statement, a block) | The calls written inside it |

Each edge is a function the call graph resolved (`node`, possibly in another file), with the call
that reaches it (`site`). Calls it could not resolve (a library, a builtin, a dynamic call) have no
edge.

```ts
const component = callees.get(element)?.find((e) => e.via === "jsx")?.node;
```

`via` says why the edge exists: `direct`, `method`, `constructor`, `jsx`, `callback` (the
function is passed to code the analysis cannot see, `items.map(f)`, and is assumed to be called),
or `type` (resolved by the receiver's type, see [Types](#types-the-typescript-7-checker)).

## Types: the TypeScript 7 checker

Values alone can't resolve `repo.save()` when `repo` is a parameter, a context object or a call
result. With types on, the TypeScript 7 checker answers instead (experimental):

- `callees` and `callers` follow `x.m()` by the type of `x`, marked `via: "type"`. For an
  interface or property-signature member, the edge goes to every class member or object property
  that implements it (up to 16; past that the call stays unresolved).
- `types(lang).typeOf.get(node)` is the type as the checker prints it: `"UserRepo"`,
  `"{ id: string; }"`. It is `undefined` with types off.

Turn them on by importing `types` in the code that uses them. That also turns on workspace analysis:

```ts
import { types } from "codemod/ast-grep";

const { typeOf } = types("typescript");
forEachFile({ include: "src/**/*.{ts,tsx}" }, (file) => {
  // typeOf.get(node) and via: "type" call edges answer here
});
```

The selector option `semanticAnalysis: { mode: "workspace", types: "ts7" }` still works, as a
deprecated shorthand for the import. In `workflow.yaml`, where there is no import:
`semantic_analysis: { mode: workspace, types: ts7 }`.

What types need:

| Need | Why |
| --- | --- |
| `typescript@7.0.x` in the target's `node_modules`, or `CODEMOD_TS_API` set to its `tsc` binary (`node_modules/@typescript/typescript-<os>-<arch>/lib/tsc`) | The checker. Other versions are not used: its protocol changes between minors. `CODEMOD_TS_API=off` turns types off everywhere |
| The target's dependencies installed (`node_modules` present), from a full install that runs before this step | Without them, everything from a library is `any` and calls on it stay unresolved. Measured: 7.6% of all calls resolved through types in a repository with dependencies installed, 1.2% across repositories without |
| A tsconfig (or jsconfig with `allowJs`) | The checker uses the nearest one; files outside any get default options. JSDoc types work in `.js` files |

Types follow [the same rule as every answer](#answers-describe-the-workspace-when-the-step-started):
the checker sees the files as they were when the step started, including earlier steps' edits in a
dry run. They cost a side process (about 200–350 MB of memory) and a few seconds on a large
workspace, the first time a query needs them.

## Is it changed: `mutations()`

Places that change the variable at the node, or the object it holds: reassignments, `++`, property
writes, `delete`, method calls, and calls it is passed to. Changes through another variable holding
the same value come back with `viaAlias: true`; changes inside a nested function with
`deferred: true`. `confidence` is `definite` (a write in the syntax), `likely` (a method known to
mutate, like `push`) or `maybe` (a call with no summary).

```ts
// moment's d.add(...) mutates d. With the result unused, rewrite to d = d.add(...);
// flag changes through aliases or callbacks for review.
for (const m of due.mutations()) {
  if (m.kind !== "method-call" || !MUTATORS.includes(m.name!)) continue;
  if (m.viaAlias || m.deferred) {
    // TODO comment: cannot rewrite in place
  }
}
// Is `items` changed after audit()? `after` takes a node of the same file.
const changed = items.mutations({ after: auditCall }).some((m) => m.confidence !== "maybe");
```

## Compare nodes: `key()` and `equals()`

Each query wraps nodes in new objects, and other files in new roots, so `===` and `id()` do not
match across answers. `node.key()` is a string (file, range, kind) that does; `a.equals(b)` compares
keys. Use keys in a `Set` or a `Map` to edit each function once; a `Map` keyed by node objects
never finds a node that came from another query.

## Rewrite imports: module resolution

In workspace scope. `file` is a path (absolute, or relative to the target), a workflow file, an
SgRoot, or a node in one:

| Call | Answer |
| --- | --- |
| `symbols(lang).resolveModule(file, "@/ui")` | The file an import in `file` resolves to (tsconfig `paths` with `extends`, workspace packages, index files), or `null` |
| `root.resolveExport("@/ui", "Modal")` | What the export lands on through barrels and `export *`: `{ node, root, kind, exportName, nameNode }`, with `exportName` `"default"` or the name |
| `symbols(lang).specifierFor(file, modal.root, { like: "@/ui" })` | A specifier `file` can import the target with, in the style of `like` (relative or alias, `.js` or not), checked by resolving it: `"@/ui/modal"` |
| `root.publicSpecifiers()` | The specifiers other packages import this file with: its package name when it is the entry (`main`, or `exports["."]`), and `exports` subpaths. Empty for private files |
| `root.hasTopLevelEffects()` | Whether importing the module runs code: a top-level call, an `import "./x"` side-effect import, or a top-level write to an object member |

`specifierFor` keeps to a workspace package's public API: for a file in another package it only
offers that package's name and its `exports` subpaths (without `exports`, only the name), never a
relative path or alias into its files. When none reaches the file, it answers `null`, and a
debarrel rewrite keeps the original import.

```ts
// A barrel can go only when skipping it skips no side effects and no other package imports it.
const keep = barrel.hasTopLevelEffects() || barrel.publicSpecifiers().length > 0;
```

`symbols(lang).definition` goes from a use of an imported name to its declaration in one call.
`@jssg/utils` builds a debarrel rewrite on these:
[`importFromDeclarations`](/community/jssg/utils/javascript#importfromdeclarations).

## Walk the workspace: lookups, `join()` and `crawl()`

Every analysis above is a **lookup**: a read-only map from a node to the edges that leave it,
`{ node, ...meta }`. Lookups combine: `crawl()` follows them, `join()` and `lookup()` add edges the
analysis can't see.

```ts
import { callGraph, crawl, dataflow, entryPoints, join, lookup, symbols, types } from "codemod/ast-grep";

const { callers, callees } = callGraph("typescript"); // meta: { site, via }
const { sources, uses } = dataflow("typescript");     // one hop back, one hop forward
const { definition, references } = symbols("typescript"); // meta: { nameNode, kind, exportName }; through imports
const { typeOf } = types("typescript");               // the TypeScript 7 checker
entryPoints("typescript");                            // function -> why it is called from outside

callees.get(handler);
// [{ node: <function loadUser>, site: <loadUser(id)>, via: "direct" }]
callers.get(unused); // undefined, like a Map
```

Code that imports `callGraph`, `types`, `entryPoints` or `join` gets workspace analysis without
`semanticAnalysis` on the selector, in `forEachFile` callbacks and in plain `step(() => ...)`
functions; importing `types` turns on the checker too. `dataflow` and `symbols` follow the step's
scope. Nodes match by syntax node (`key()`), so a node from another query finds its edges.
Built-in lookups are answered node by node and can't be listed: `size`, `keys()` and `for...of`
throw. Like every answer, they describe the workspace when the step started.

### Edges you know: `lookup()`

When you know edges the analysis can't see, build a lookup from `[from, to, meta?]` pairs. Both ends
must be nodes; the error names the edge that is not. It lists its edges like a Map.

```ts
const renders = lookup(pages.map((page) => [page, layoutOf(page), { via: "layout" }]));
```

### Edges between two patterns: `join()`

Most framework edges are a pattern on one side and a pattern on the other, joined where a captured
name is equal: a tRPC call to its procedure, `emit("x")` to `on("x")`, a Django URL to its view.
`join()` builds that lookup in one pass, with no JavaScript per match:

```ts
const procedures = join({
  from: { find: "trpc.$R.$P.$M($$$)", anchor: "function", on: "$P" }, // the edge starts at the calling function
  to: { find: { rule: { pattern: { context: "({ $P: publicProcedure.$M($$$) })", selector: "pair" } } }, on: "$P" },
  meta: { via: "trpc" },
});
procedures.get(Profile);
// [{ node: <getUser: publicProcedure.query(...)>, site: <trpc.user.getUser.useQuery()>, name: "getUser", via: "trpc" }]
```

`find` is a pattern, or a rule as `findAll()` takes. `anchor: "function"` puts the edge on the
function around the match instead of the match.

Two captures join when they name the same thing. Where both resolve (an imported function, a
variable), that means the same declaration, so two files that each register their own `handler`
don't get crossed; where either doesn't (a string like an event name, a property the analysis can't
follow), it means the same text. Results get more precise with [types](#types-the-typescript-7-checker)
on: a tRPC client's `trpc.user.getUser` resolves only through the checker, so without it procedures
join by name. To choose, pass `by`:

| `by` | Joins when |
| --- | --- |
| (left out) | Both resolve to the same declaration; otherwise the text is equal |
| `"text"` | The text is equal |
| `symbols("typescript").definition`, or any lookup | Both resolve, through it, to the same node; the rest are dropped |

A route path `"/users/[id]"` against a fetch of `` `/users/${id}` `` needs code to normalize, so build
those edges with `lookup()`.

### Follow edges: `crawl()`

`crawl(lookups, start, { stopAt })` walks one or more lookups from the start nodes, breadth first,
each node once, and maps each node it reached to the edge that reached it first (with `from`, the
node it came from). Start nodes map to `null`. It reaches a `stopAt` node but does not walk past it.

```ts
// Everything a page can run, through tRPC and plain calls
const reached = await crawl([procedures, callees], Profile);
for (const [node, edge] of reached) {
  console.log(edge ? `${edge.from.text()} -> ${node.text()} (${edge.via})` : `start: ${node.text()}`);
}
```

A function with callers can still be dead. To check, crawl from the entry points:

```ts
const live = await crawl(callees, entryPoints("typescript"));
const dead = exported.filter((fn) => !live.has(fn));
```

`crawl()` takes lookups only. To crawl edges you hold in a `Map`, make it one with
`lookup([...map].flatMap(([from, tos]) => tos.map((to) => [from, to])))`.

### Across steps: nodes are keys

A step's result is JSON, so a node a step returns is its key, and a lookup or a crawl's result is
its edges with keys for nodes. Anywhere an analysis takes a node (`get()`, `crawl()`'s start and
`stopAt`, `lookup()`'s edges), its key works too. `lookup(result)` makes a returned lookup or crawl
result a lookup again:

```ts
const routes = await step(() => join({ /* ... */ }));          // a lookup, as JSON
const reached = await step(() => crawl([lookup(routes), callees], startKey));

await step(forEachFile({ language: "typescript" }, (file) => {
  const live = lookup(reached);                                  // a crawl's result again
  const root = parse(file).root();
  // ... edit what live.has(node) says was reached
}));
```

Keys name nodes in the files as the step starts. A key from before an earlier step changed its file
no longer names a node, and using it fails with the key in the message; find the node again after
the edit. In a dry run, keys name nodes as earlier steps left the files in memory.

## Cookbook

Short recipes taken from codemods built on these queries. Each one rewrites only when the answer
is complete, and flags the rest.

### Is this SQL built from request data?

```ts
// db.query("select ... " + id) -> db.query("select ... ?", [id])
for (const call of root.root().findAll({ rule: { pattern: "$DB.query($SQL)" } })) {
  const sql = call.getMatch("SQL")!;
  const origins = await crawl(dataflow("typescript").sources, sql);
  if (![...origins.values()].some((e) => e?.kind === "parameter" && e.name === "req")) continue;
  // The text is built in the argument, or in the variable passed: its initializer.
  const init = [...origins].find(([, e]) => e?.via === "assign" && origins.get(e.from)?.kind === "variable");
  const built = sql.is("identifier") ? init?.[0] : sql;
  // ...split `built` into text and parameters, then edit `built` and the call's arguments
}
```

### Delete exported functions nobody uses

```ts
const { callers } = callGraph("typescript");
const { references } = symbols("typescript");
const outside = entryPoints("typescript");
for (const fn of root.root().findAll({ rule: { kind: "function_declaration", inside: { kind: "export_statement" } } })) {
  const name = fn.field("name")!;
  // Called from outside the workspace (a package export, a route handler): keep it.
  if (outside.has(fn)) continue;
  if (callers.get(fn)?.length) continue;
  // No callers is not enough: a function stored as a value is referenced, not called,
  // and a getter or setter runs on property reads and writes, which are not calls.
  if ((references.get(name) ?? []).some((r) => !r.node.equals(name))) continue;
  // ...remove the export statement
}
```

### Make a function async, and every caller

```ts
const { callers } = callGraph("typescript");
const reached = await crawl(callers, loadConfig);
for (const fn of reached.keys()) {
  for (const edge of callers.get(fn) ?? []) {
    if (edge.via === "callback") continue; // names.map(getSetting): add a TODO at edge.site instead
    // edit: `await ${edge.site.text()}` in edge.site.getRoot()
  }
  // make fn async (crawl reaches each function once); a callback edge's function is not followed
}
```

### Import from declarations instead of a barrel

```ts
import { importFromDeclarations } from "@jssg/utils/javascript/modules";

const statements = root.root().findAll({
  rule: { any: [{ kind: "import_statement" }, { kind: "export_statement", has: { field: "source", kind: "string" } }] },
});
const edits = statements.map((s) => importFromDeclarations(root, s)).filter(Boolean);
// import { Button, Modal } from "@/ui"  ->  import { Button } from "@/ui/button"; import Modal from "@/ui/modal"
```

Then, on the barrel itself, decide whether it can go: it has no code of its own, no
`root.hasTopLevelEffects()`, no `root.publicSpecifiers()`, and every import of it can be pointed at
the declarations (no namespace import, no `require`, no dynamic import whose members are unknown). Run a type check after the codemod and restore any barrel named in a new error.

### Type-check gate

A codemod that removes or moves files (a barrel set aside as `index.barrel.bak.ts`) should prove
the project still type-checks, and undo the changes that broke it. The checker runs in workflow
`shell` steps; [`@jssg/utils/javascript/typecheck`](/community/jssg/utils/javascript#type-check-gate)
maps its errors back to the changes:

```ts workflow.ts
import { step, forEachFile, shell, fail } from "codemod/workflow";
import { parseTypeErrors, newTypeErrors, typeErrorCauses } from "@jssg/utils/javascript/typecheck";
import debarrel from "./scripts/debarrel.ts"; // a forEachFile callback: rewrites imports, file.rename()s barrels

export default async function main() {
  const tsc = () => shell("npx tsc --noEmit -p . --pretty false", { allowFailure: true });
  const before = parseTypeErrors((await step("Type check (before)", tsc())).stdout);

  await step(
    "Debarrel",
    forEachFile({ include: "src/**/*.{ts,tsx}", language: "tsx", semanticAnalysis: "workspace" }, debarrel),
  );

  // The barrels the codemod set aside.
  const { stdout } = await step("Removed barrels", shell("git ls-files --others --exclude-standard -- '*.barrel.bak.*'"));
  const removed = stdout.split("\n").filter(Boolean)
    .map((bak) => ({ from: bak.replace(".barrel.bak", ""), to: null, bak }));

  const after = parseTypeErrors((await step("Type check (after)", tsc())).stdout);
  const causes = typeErrorCauses(newTypeErrors(before, after), removed);

  // Put back each barrel a new error points at, then check once more.
  const restore = removed.filter((change) => causes.has(change));
  if (restore.length > 0) {
    for (const change of restore) await step(`Restore ${change.from}`, shell`mv ${change.bak} ${change.from}`);
    const again = newTypeErrors(before, parseTypeErrors((await step("Type check (again)", tsc())).stdout));
    if (again.length > 0) fail(`${again.length} new type errors after restoring ${restore.length} barrels`);
  }
  if (causes.has(null)) fail(`${causes.get(null)!.length} new type errors not caused by a removed barrel: review the edits`);
}
```

A restored barrel's consumers stay rewritten: the barrel comes back for whatever still needed it
(an import the codemod could not see, such as a non-TypeScript consumer or a generated file). The
step names say which barrels were restored.

## Python

The same methods and lookups work on `.py` files, with `"python"` as the language. Python support is simpler than JavaScript's:

- Names are resolved with Python's scoping rules (module, function, class and comprehension
  scopes, `global`, `nonlocal`), not with a type checker.
- Imports resolve to workspace files: `import a.b`, `from a import b`, relative imports
  (`from .services import f`, `from . import services`) and re-exports from a package's
  `__init__.py`. Installed packages are not looked into, so calls into them have no callee edge.
- Types come from annotations only. A call on an annotated receiver resolves to the class's
  method: with `repo: OrderRepository`, `repo.find()` is `OrderRepository.find`. The same goes
  for return annotations (`def get_repo() -> OrderRepository`), annotated class attributes and
  `self.x = x` assigned in a method. `self.method()`, `super().method()` and `Class()` (its
  `__init__`) resolve too. `types("python").typeOf` answers the annotation as written.
- f-strings, `%` and `.format()` derive from their parts, so a request value is followed into
  `cursor.execute(f"…")` or SQLAlchemy's `text(f"…")`.
- A decorator is a call of the decorator with the function: `@app.get("/")` and `@shared_task`
  show up as `callback` callers. `task.delay(…)` and `task.apply_async(…)` call the task.
- `mutations()` knows the list, dict and set methods that change their receiver (`append`,
  `update`, …), and `setattr`/`delattr`.


## Soundness: what "may" means

The analysis is **not sound**: JavaScript makes that unaffordable. It over-approximates inside what
it models and says where it stops. Build automatic rewrites only on complete answers; flag the rest.

| What it gives up | How you see it |
| --- | --- |
| Values from outside the module: parameters, imports, globals, `this` | `boundary: true` on the step |
| Calls it cannot resolve (libraries, builtins, dynamic calls) | No `callees` edge. Flow treats the result as derived from the arguments, so taint is not lost |
| Order of execution | Flow-insensitive: both values of a `let` assigned twice are sources. `mutations({ after })` uses text order plus "same loop" |
| Heap: `o.p = x`, then `o.p` read elsewhere | `uses` reports the write (`via: "store"`) and stops |
| Closures: a callback that reads `x` | Not a flow edge. A mutation inside a nested function is `deferred` and always counts as "after" |
| Control dependence: `c ? a : b` | `a` and `b` are sources, `c` is not |
| Whether an unknown method mutates | `confidence: "maybe"` |
| Callbacks handed to unknown code | Assumed called: `via: "callback"`. Can be a false edge |
| Namespace members (`ns.fn` stored or passed as a value) | `symbols(lang).references` finds `ns.fn` uses through `import * as ns`; check it alongside `callers` before deleting |
| Files that do not parse | Their calls are not in the call graph; asking about one throws |
| Edits during a run | Every answer describes the workspace when the step started: a step sees earlier steps' edits, never its own. A query on a root parsed from text the step produced throws |
| Callers from outside the workspace | `callers` lists call sites only. Package exports and declared rules are in `entryPoints(lang)` |
| Types (with `types` imported) | `via: "type"` edges trust the declared type: a value cast with `as` or typed `any` is followed as declared, or not at all |

### When the answer is "can't tell"

- **Rewrite** when the answer is complete and has no boundary or `maybe` on the path that matters.
- **Flag** (a TODO comment, a report entry, an agent step) when a `boundary`, a call with no callee
  edge, `maybe` or `callback` touches the decision.
- **Never delete on an empty answer alone.** Check completeness and `symbols(lang).references`.

## Performance

- `mutations` and `dataflow(lang)` touch one file: facts are built the first time a query
  touches it and cached by content.
- `callees` builds facts only for the files it reaches, and so does a `crawl()` over it.
- The first `callers` query in a step (and `references` in workspace scope) walks the whole
  workspace once, in parallel, and keeps a table for the rest of the step. Each step that asks
  builds its own, so a run that asks `callers` in many steps pays this once per step. Measured on a 2,500-file, 13 MB
  workspace: about a second for that first query, then well under a millisecond per query. At
  24,000 files (132 MB of source) the first query takes about 13 seconds and the run peaks at about
  3.5 GB of memory: in very large repositories, prefer file-local queries or narrow the target.
- Prefer `stopAt` to filtering a long crawl.
